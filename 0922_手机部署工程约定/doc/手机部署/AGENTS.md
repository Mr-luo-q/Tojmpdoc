## 协作原则

### 少说废话

表达要切实具体。少做空泛总结，少堆无用标题，少讲正确的废话。

少用“不是，而是”这种表述！！！

少用无序列表！！
小步骤不要用无序列表或者有序列表，都用代码框里画图，列举时同理

### 多使用代码框里画图梳理！！

### 代码要配备同名中文.md文档讲解

每写一份代码，无论是.py还是.json都配置一份.md，对于.py就进行输入输出，功能讲解，对于.json就总结数据内容，如果数据不长，就完整用人类好读懂的方式展现

如果修改代码，必须修改对应同名中文md文档

### 写代码时每一个模块，每一个函数至少有一行中文注释

### 合理分点，不要让句子高度碎片化

合理分点，但分点必须服务于结构。
写文档时，不要把句子机械拆成大量碎片化 bullet，不要分太多细碎的小点（一点一行那种）！！
鼓励使用代码框画递进式结构图
写文档时，不要把句子机械拆成大量碎片化 bullet。
即禁止如下这种写法：
text
甲如何如何：

- A
- B
- C
  乙如何如何：
- X
- Y
- Z
  丙如何如何：
- M
- N

### 先抓核心

先判断真正的问题，再决定修改范围。不要被表面现象牵着走，不要头痛医头、脚痛医脚。

要先想清楚：

1. 根因在哪里
2. 是单点问题还是结构性问题
3. 正确的修复层级在哪一层

### 广泛搜索信息

搜索不要局限于本地。要主动结合：

1. 本地代码、文档、配置、数据、历史实现
2. 互联网资料、官方文档、外部参考实现、最新可验证信息

不要只看当前打开的文件，也不要只凭记忆下结论。

### 分析别人内容时，多举例子

分析别人的代码、文章、设计方案或技术路线时，不要空泛概括，要用具体例子把判断讲清楚。

### 拒绝打补丁式修改

如果根因在数据结构、派生逻辑、渲染层次、模块边界或状态流转，就应当在正确层级系统修正，而不是只改表面参数或局部现象。

### 修改后形成验证闭环

代码改完不算结束。尽量形成“修改 -> 运行 -> 观察 -> 修正”的闭环。

尤其是前端、2D/3D viewer、渲染、交互、样式、布局这类任务，要主动：

1. 启动程序或服务
2. 打开实际界面查看结果
3. 必要时自动截图
4. 将截图上传模型，根据结果继续修正

关于截图验证：

1. 截图不是为了留痕，而是为了减少主观判断
2. 遇到视觉、布局、透明度、层级、交互结果这类问题时，截图通常比口头描述更可靠
3. 截图后要对照预期检查整体效果，不一致就继续修正

### 先验证，再下结论

没有验证前，不要轻易说”已经解决”或”应该没问题”。

总结时区分：

1. 已验证的事实
2. 基于现象的推断
3. 仍待确认的风险

### 工程设计文档风格

写工程设计文档时，优先写成“可实现规格书”，不要写成“咨询分析报告”。

```text

每个模块尽量按固定模板写：

模块名

职责：
  ...

输入：
  ...

输出：
  ...

读取：
  ...

写入：
  ...

不负责：
  ...

对应文件：
  ...
少写抽象判断，多写状态怎么流转、谁读谁写、文件如何落地。

不要只说“这个模块很重要”“应该解耦”“边界要清晰”。
必须落到：

数据结构是什么
接口是什么
状态归谁写
调用顺序是什么
失败时返回什么
对应文件在哪里
```

### 约束 LLM 输出：只给信息，不要表演

给 LLM 写 system prompt 时，必须明确加入以下约束。GPT 在拿到工具后倾向于把每次响应当成”向用户汇报”，反复总结、反复列表、反复加 emoji——这在 agent 交互中是噪音。

**必须遵守：**

1. **不重复**：同一个结论只说一次。不要在 Step 5 说了一遍温度降了 2.7°C，Step 6 又列表说一遍，Step 7 再表格说一遍。信息密度比信息长度重要。
