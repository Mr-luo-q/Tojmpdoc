# Token 速率详表 · Redmi K70E

实测日期：2026-10-09
设备：Redmi K70E（`duchamp`），MediaTek MT6897 = 天玑 8300-Ultra
后端：llama.cpp 0.6.0（Termux 官方包），**纯 CPU**
模型：Qwen2.5-1.5B-Instruct Q4_K_M、Qwen3-0.6B Q4_K_M

## 一、先分清两个阶段

Token 速率不是"一个数字"，是**两个性质完全不同的阶段**：

```text
prefill（提示词处理 / prompt processing，pp）
    把整段提示词一次性喂进模型，做大批量矩阵乘
    性质：计算受限（compute-bound）
    影响因素：提示词长度、批大小、核心数、主频
    体验对应：敲完问题到模型开始吐字之前的等待
    对应指标：首字延迟（TTFT）

decode（逐 token 生成 / text generation，tg）
    一次生成一个 token，每生成一个都要把全部权重从内存读一遍
    性质：访存受限（memory-bandwidth-bound）
    影响因素：模型体积、内存带宽、上下文深度
    体验对应：模型吐字的速度，俗称「每秒多少字」
```

**这两个阶段对同一组参数的响应方向经常相反。** 本机有现成例子（第四节）：线程数从 4 加到 8，prefill 基本不变，decode 却掉一半。所以任何"这台手机跑多少 t/s"的说法，不指明是哪个阶段就没有意义。

## 三、Prefill 速率（提示词处理）

测量条件：`-ngl 0 -t 4 -r 2 --no-warmup`（下方标注除外）

### 3.1 Qwen2.5-1.5B

| 提示词长度 | t/s | 标准差 | 该长度耗时 |
|---|---|---|---|
| 32 | 18.28 | ± 0.02 | 1.8 s |
| 64 | 18.37 | ± 0.03 | 3.5 s |
| 128 | 18.44 | ± 0.06 | 6.9 s |
| 256 | 18.45 | ± 0.03 | 13.9 s |
| 512 | 18.40 | ± 0.01 | 27.8 s |
| 1024 | 18.15 | ± 0.01 | 56.4 s |
| 2048 | 17.70 | ± 0.04 | 115.7 s |

**平台型曲线**：几乎不随长度变化，稳定在 18.4 t/s 附近，长提示词时略降（2048 时比峰值低 4%）。

正常情况下一段 2048 token 的提示词应该比 32 token 摊薄得更好、速度应该上升。这里不升反降，说明**本机的 prefill 没有从大批量里获得收益**，单次矩阵乘的规模还没大到能压过缓存与带宽压力，或者已被某个环节限住。标准差 ±0.01~0.06 说明曲线形状是真实的。

### 3.2 带预热的对照

同一台机器、同一参数，但去掉 `--no-warmup`（`-r 3`）：

| 提示词长度 | 无预热（条件乙） | 带预热（条件甲） | 差异 |
|---|---|---|---|
| 512 | 18.40 | 22.42 | +21.8% |
| 1024 | 18.15 | 20.61 | +13.6% |
| 2048 | 17.70 | 19.20 | +8.5% |

**预热让 CPU 升频到位，数值系统性偏高 8~22%。** 两种条件都有价值：条件甲反映持续使用的稳态，条件乙反映每次全新请求。日常多轮对话更接近条件甲。

### 3.3 Qwen3-0.6B

| 提示词长度 | t/s | 标准差 | 该长度耗时 |
|---|---|---|---|
| 32 | 47.85 | ± 0.58 | 0.7 s |
| 64 | 46.66 | ± 0.42 | 1.4 s |
| 128 | 49.44 | ± 2.70 | 2.6 s |
| 256 | 51.78 | ± 0.02 | 4.9 s |
| 512 | 52.24 | ± 0.11 | 9.8 s |
| 1024 | 待补 | — | — |
| 2048 | 待补 | — | — |

与 1.5B 不同的地方：**0.6B 的 prefill 随长度略微上升**（47.85 → 52.24，+9%），说明它在较大批量下能获得一点收益。1.5B 是持平略降，0.6B 是缓升——小模型的计算密度低，大批量更能摊薄固定开销。

pp128 那格标准差 ±2.70 偏大（均值的 5.5%），可能与测量期间后台有 `llama-server` 常驻进程有关，该点可信度略低。

### 3.4 提示词长度换算成实际等待

用户感知的是"等多久"，不是 t/s。换算（取无预热条件的偏低值，属保守估计）：

```text
提示词 128 token   →  6.9 秒
提示词 512 token   →  27.8 秒
提示词 2048 token  →  115.7 秒（接近两分钟）
```

**这是这台机器最拖体验的一环。** 512 token 的提示词（约 300~400 汉字）要等近半分钟才出第一个字。

## 四、Decode 速率（逐 token 生成）

### 4.1 生成长度曲线

测量条件：`-ngl 0 -t 4 -r 2 --no-warmup -p 128`

| 生成长度 | 1.5B t/s | 1.5B 标准差 | 0.6B t/s | 0.6B 标准差 |
|---|---|---|---|---|
| 16 | 15.02 | ± 0.47 | 31.72 | ± 0.30 |
| 32 | 14.61 | ± 0.05 | 31.36 | ± 0.26 |
| 64 | 14.55 | ± 0.12 | 30.85 | ± 0.16 |
| 128 | 14.45 | ± 0.02 | 30.15 | ± 0.02 |
| 256 | 13.55 | ± 0.67 | 28.30 | ± 0.03 |
| 512 | **12.50** | ± 0.00 | **23.90** | ± 0.04 |

**生成越长越慢**，原因明确：KV 缓存持续增长，每生成一个 token 都要扫描越来越多的历史键值对。

```text
1.5B  从 15.02（16 token）降到 12.50（512 token），衰减 16.8%
0.6B  从 31.72（16 token）降到 23.90（512 token），衰减 24.6%
```

有趣的是 **0.6B 的衰减反而更大**。合理推测：0.6B 权重小、单步计算量小，KV 扫描在总时间里的占比更高，所以受上下文增长的影响更明显。而 1.5B 的单步权重读取本身就占了大头，KV 增量的相对影响被稀释。

**实用含义：短回答（几十个 token）能吃到最高速度；长回答会逐步变慢。** 若要一口气生成长文，按 512 token 的 12.5 t/s 估算更接近实际。

### 4.2 线程数：两个阶段方向相反（最关键的一组）

测量条件：`-ngl 0 -p 512 -n 128 -r 3`（带预热）

| 线程数 | pp | tg |
|---|---|---|
| 4 | 约 22 | **约 15~16** |
| 6 | 约 21 | 约 11 |
| 8 | 约 22 | **约 7.8** |

```text
prefill   线程越多越好，4→8 基本持平（21~22）
decode    线程越多越差，4→8 掉了一半以上
```

**原因**：三个簇的频率跨度大（2.2 / 3.2 / 3.35 GHz）。`-t 4` 时线程集中在一个簇内，缓存局部性好；`-t 6`、`-t 8` 让线程跨簇分布，**同一个 token 的计算要在不同簇之间同步与迁移，缓存行反复失效**。decode 是访存受限的，缓存效率直接决定速度，受害最重；prefill 是计算受限的，多核算力的收益盖过了缓存损失。

**结论：日常必须用 `-t 4`。** 这个坑很隐蔽，因为"用满 8 核"看起来才符合直觉。

### 4.3 绑核实测：小核不能用于推理

测量条件：`taskset -c <掩码> llama-bench -p 128 -n 48 -ngl 0 -r 2`，模型 1.5B

| 绑定核心 | 线程 | pp128 | tg48 |
|---|---|---|---|
| cpu0-3（4×A510 2.2GHz） | 4 | 3.46 | **2.60** |
| cpu4-6（3×A715 3.2GHz） | 3 | 17.07 | 12.50 |
| cpu7（1×A720 3.35GHz） | 1 | 5.76 | 4.34 |
| cpu0-7（全部） | 8 | **24.23** | 8.13 |
| cpu4-7（中+大核） | 4 | 21.70 | **14.93** |

**四个小核单独跑 decode 只有 2.60 t/s，是大核集群（12.50）的 1/5。**

另一个关键观察：把线程**限制**在 cpu4-7（4 个核）时的 decode（14.93）**高于**放开全部 8 核（8.13）。所以不是"核越多越快"，而是"核越集中越快"。

## 五、上下文深度的影响（长对话场景）

测量条件：`-ngl 0 -t 4 -r 2 --no-warmup -p 128 -n 64 -d <深度>`

`-d` 的语义：先预填充 n 个 token 作为已有上下文，再测 pp/tg。模拟"对话进行到第 n 个 token 时"的表现。

### 5.1 Qwen2.5-1.5B

| 上下文深度 | pp128 | tg64 | 相对 d=0 的 tg 变化 |
|---|---|---|---|
| 0 | 17.11 ± 0.81 | 13.36 ± 0.04 | 基准 |
| 512 | 16.94 ± 1.27 | 11.07 ± 0.00 | **−17.1%** |
| 1024 | 17.26 ± 0.02 | 10.07 ± 0.03 | **−24.6%** |
| 2048 | 16.26 ± 0.05 | **7.38** ± 0.14 | **−44.8%** |

### 5.2 Qwen3-0.6B

| 上下文深度 | pp128 | tg64 | 相对 d=0 的 tg 变化 |
|---|---|---|---|
| 0 | 46.32 ± 0.09 | 27.56 ± 0.18 | 基准 |
| 512 | 43.13 ± 1.55 | 17.10 ± 0.01 | **−37.9%** |
| 1024 | 43.15 ± 0.06 | 13.00 ± 0.13 | **−52.8%** |
| 2048 | 36.77 ± 0.01 | **8.90** ± 0.07 | **−67.7%** |

### 5.3 三条结论

**第一，prefill 对深度不敏感，decode 对深度极敏感。**

```text
1.5B  pp  17.11 → 16.94 → 17.26 → 16.26    基本持平（2048 才降 5%）
      tg  13.36 → 11.07 → 10.07 →  7.38    持续大幅下滑
```

这是访存受限的教科书式表现：

```text
prefill   整段提示词一次性做批量矩阵乘，KV 变长带来的额外扫描
          被批量并行摊薄，所以几乎无感
decode    每生成一个 token 就要扫描全部历史 KV，
          上下文翻倍则扫描量翻倍，直接体现在速度上
```

**第二，0.6B 在长上下文下衰减得比 1.5B 严重得多。**

```text
                 d=0      d=2048    衰减
    1.5B        13.36      7.38     −44.8%
    0.6B        27.56      8.90     −67.7%
```

**这是选择模型时容易忽略的一点。** 0.6B 在短上下文下比 1.5B 快一倍（27.56 vs 13.36），但到了 2048 深度，两者几乎持平（8.90 vs 7.38），0.6B 的优势被吃掉了 80%。

原因推测：0.6B 的权重读取本身很快，KV 扫描在总时间里的占比因此更高；上下文一长，KV 就变成主导项。1.5B 的权重读取本来就占大头，KV 增量的相对影响被稀释。

**第三，越深衰减越陡（不是线性的）。**

```text
1.5B  每翻一倍的衰减    512 → 17.1%    1024 → 再加 7.5%    2048 → 再加 20.2%
0.6B  每翻一倍的衰减    512 → 37.9%    1024 → 再加 14.9%   2048 → 再加 14.9%
```

从 1024 到 2048 这一档的衰减明显加速，说明超过某个深度后，KV 扫描（以及可能的缓存失效）开始主导。

### 5.4 实用含义

```text
长对话会显著变慢，而且比预期严重。

    在 1024 深度    1.5B decode 已从 13.36 降到 10.07（−25%）
    在 2048 深度    1.5B 降到 7.38（−45%），0.6B 降到 8.90（−68%）

对策：
    1. 及时开新会话，不要无限累积上下文
       这是最有效的单一手段
    2. 若必须长上下文，把 -c 设在真正需要的长度
       设成 4096 而实际只用 1000，只会白白增加内存与 KV 压力
    3. 如果对话会很长，1.5B 的衰减比 0.6B 温和，
       长对话场景下两者的差距会缩小甚至反转
```

对第 3 点的具体说明：

```text
短对话（深度 < 512）    0.6B 快约 2 倍，优势明显
长对话（深度 2048）     0.6B (8.90) 只比 1.5B (7.38) 快 21%
                       而 1.5B 的回答质量更高
→ 长对话场景下 1.5B 反而可能是更好的选择
```

## 六、真实 HTTP 请求实测（含首字延迟 TTFT）

前面几节的数据来自 `llama-bench`，是**纯计算**的分阶段值，排除了 HTTP 层、对话模板套用、token 采样等开销。这一节测真实接口，反映用户实际感受到的延迟。

测量方式：`curl -X POST /v1/chat/completions`，`stream: false`，读取 `time_starttransfer` 与 `usage` 字段。

### 6.1 Qwen2.5-1.5B（`-t 4 -c 2048 -ngl 0`）

| 请求 | 首字延迟 | 提示词 token | **命中缓存** | 生成 token | 总耗时 | decode |
|---|---|---|---|---|---|---|
| `Say hi.`（max 1） | 1.79 s | 32 | **0** | 1 | 1.79 s | — |
| `Say hi.`（max 32） | **0.82 s** | 32 | **31** | 10 | 0.82 s | 12.2 t/s |
| `Write a short paragraph about the ocean.` | 8.85 s | 37 | 24 | 106 | 8.85 s | **11.98 t/s** |

### 6.2 Qwen3-0.6B（`-t 4 -c 2048 -ngl 0`）

| 请求 | 首字延迟 | 提示词 token | 命中缓存 | 生成 token | 总耗时 | decode |
|---|---|---|---|---|---|---|
| `Say hi.`（max 1） | **0.36 s** | 15 | 0 | 1 | 0.36 s | — |
| `Say hi.`（max 32） | 0.40 s | 15 | 14 | 10 | 0.40 s | 25.3 t/s |
| `Write a short paragraph about the ocean.` | 3.44 s | 20 | 3 | 89 | 3.44 s | **25.86 t/s** |

### 6.3 三个必须注意的点

**第一，首字延迟差距远大于 decode 差距。**

```text
首字延迟（近似 TTFT）
    1.5B   1.79 s
    0.6B   0.36 s        ← 快 5.0 倍

decode
    1.5B   11.98 t/s
    0.6B   25.86 t/s     ← 快 2.2 倍
```

首字延迟由 prefill 主导，而 prefill 直接与权重体积相关——0.6B 的权重只有 1.5B 的 35%，所以首字快得多。**如果在意"响应快"，0.6B 的收益在首字上比在 decode 上更明显。**

**第二，HTTP 的 decode 值低于 llama-bench，差值就是接口层代价。**

```text
1.5B   llama-bench tg64 = 14.55    HTTP 实测 = 11.98    差 17.7%
0.6B   llama-bench tg64 = 30.85    HTTP 实测 = 25.86    差 16.2%
```

约 16~18% 的差值来自 HTTP 处理、对话模板套用、采样器开销、JSON 序列化。属于正常范围，若超过 30% 才值得排查。

**第三，也是最重要的一点——提示词缓存（cached_tokens）效果巨大。**

```text
1.5B 极短请求   prompt_tokens=32  cached_tokens=0    首字延迟 1.79 s
1.5B 短请求     prompt_tokens=32  cached_tokens=31   首字延迟 0.82 s
```

**同样的 32 token 提示词，命中 31 个 token 的缓存后，首字延迟从 1.79 秒降到 0.82 秒（快 2.2 倍）。**

机制是：llama.cpp 会把已处理过的提示词前缀的 KV 缓存保留下来。多轮对话时，新提问与历史共享同一段前缀，那部分无需重新做 prefill，只需处理新增的几个 token。

**这解释了为什么多轮对话的体感比单次长提示词好得多**，也是为什么第一节算出的"512 token 要等 27.8 秒"属于最坏情况——那是完全无缓存的全新提示词。

由此得出两条实用建议：

```text
1. 多轮对话比"每次把全部背景重新贴一遍"快得多
   后者每次都让缓存失效，等于每次重付满额 prefill

2. 把固定背景放在对话开头，之后追加问题
   前缀不变则缓存一直生效，首字延迟能稳定在 1 秒内
```

## 七、两种模型的横向对比

| 指标 | Qwen2.5-1.5B | Qwen3-0.6B | 比值 |
|---|---|---|---|
| 模型体积 | 1065 MB | 378 MB | 2.82 |
| 参数量 | 1.78 B | 596 M | 2.99 |
| prefill（pp128） | 18.44 | 49.44 | 2.68 |
| prefill（pp256） | 18.45 | 51.78 | 2.81 |
| decode（tg64） | 14.55 | 30.85 | 2.12 |
| decode（tg512） | 12.50 | 23.90 | 1.91 |
| decode @ d2048 | 7.38 | 8.90 | 1.21 |
| 首字延迟（HTTP） | 1.79 s | 0.36 s | 4.97 |
| 常驻内存 | 约 1.9 GB | 约 0.7 GB | — |

**三个值得注意的地方：**

**第一，prefill 的比值严格吻合权重体积比，decode 明显偏低。**

```text
prefill 比值 2.81  ≈  权重体积比 2.82     完全吻合
decode  比值 2.12  <   权重体积比 2.82     明显更低
```

prefill 是计算受限，时间与参数量成正比，所以比值吻合。decode 是访存受限，按"体积 ÷ 带宽"反推有效带宽：

```text
1.5B   1.065 GB ÷ (1 / 14.55) ≈ 15.5 GB/s
0.6B   0.378 GB ÷ (1 / 30.85) ≈ 11.7 GB/s
```

**0.6B 的有效带宽反而更低（11.7 vs 15.5 GB/s）**，说明小模型没能把带宽压榨得更充分——固定开销（KV 读写、激活、调度）在总时间里的占比上升了。但因为权重只有 35%，净速度仍快一倍多。

**这是"选小模型"策略的典型表现：速度取决于「体积 ÷ 带宽」，小模型在体积上赢的幅度远大于带宽效率上的损失。**

**第二，首字延迟的差距（5 倍）远大于 decode 的差距（2 倍）。**

首字延迟由 prefill 主导，而 prefill 直接与权重体积挂钩。**在意"响应快"的话，0.6B 的收益在首字上最明显。**

**第三，长上下文会反转结论。**

```text
decode @ 深度 0       0.6B 快 2.12 倍
decode @ 深度 2048    0.6B 只快 1.21 倍
```

上下文一长，0.6B 的速度优势被大幅侵蚀。**长对话场景下 1.5B 可能是更好的选择**——速度差距缩小到 21%，而回答质量更高。

## 八、三个后端的横向对比（CPU / GPU / NPU）

前面几节全是 CPU 的数据。这一节把 GPU 与 NPU 也放进来，用**完全相同的参数与条件**测一遍，避免"拿不同参数的数字并列"这种不严谨的比较。

### 8.1 统一测量条件

```text
模型    Qwen2.5-1.5B 与 Qwen3-0.6B
参数    -p 128  -n 64  -r 3  --no-warmup
线程    -t 4（CPU 侧最优）
GPU 卸载量
    1.5B  用 -ngl 8   （全量 -ngl 99 会挂死，见 GPU-NPU加速实测报告.md）
    0.6B  用 -ngl 99 与 -ngl 8 各测一次，-ngl 99 是 GPU 最好的情况
```

### 8.2 实测结果

| 模型 | 后端 | pp128 | tg64 | pp 相对 CPU | tg 相对 CPU |
|---|---|---|---|---|---|
| 1.5B | **CPU** `-ngl 0` | **27.60 ± 1.00** | **18.46 ± 0.42** | 基准 | 基准 |
| 1.5B | GPU `-ngl 8` | 6.21 ± 0.15 | 0.90 ± 0.00 | 慢 4.4 倍 | **慢 20.5 倍** |
| 0.6B | **CPU** `-ngl 0` | **72.75 ± 0.34** | **42.55 ± 0.52** | 基准 | 基准 |
| 0.6B | GPU `-ngl 99` | 15.51 ± 2.22 | 22.41 ± 1.07 | 慢 4.7 倍 | 慢 1.9 倍 |
| 0.6B | GPU `-ngl 8` | 13.39 ± 1.70 | 2.60 ± 0.00 | 慢 5.4 倍 | 慢 16.4 倍 |

**GPU 唯一接近 CPU 的配置是 0.6B 全量卸载的 tg（22.41 vs 42.55），仍慢 1.9 倍。** 其余全面慢 4~20 倍。

### 8.3 NPU：无法给出速度数字

NPU 在这份对比表里是空的，**不是漏测，是没有入口**。三层验证的结论：

```text
L1  /dev/apusys 存在但 App 域不可读写
    注意：权限位写着 crw-rw-rw-，看起来人人可用，
    但以 u:r:runas_app:s0 身份 dd 读一个字节直接被拒
    → 拦它的是 SELinux 域策略，不是文件权限

L2  /vendor/lib64 下的 libneuron_runtime.so / libapu_mdw.so /
    libtflite_mtk.so 全部被 linker namespace 拒绝
    （Termux 进程的 permitted_paths 里没有 /vendor/lib64）

L3  NNAPI 能枚举到 4 个加速器，这是唯一的好消息：
        mtk-dsp_shim / mtk-mdla_shim / mtk-neuron_shim / nnapi-reference
    但：
      · 手工用 NNAPI C API 建图卡在 ANeuralNetworksOperandType 的 ABI 校验
        四种结构体布局（24/32/24/40 字节）× 两种类型常量，全返回
        ANEURALNETWORKS_BAD_DATA（4）
      · TFLite runtime 这个构建没有编入 NNAPI delegate
        （tflite.NnApiDelegate 属性不存在，load_delegate 报
         undefined symbol: tflite_plugin_create_delegate）
```

**更根本的阻断在格式层面，与 ABI 能否打通无关：**

```text
NNAPI 吃的是 TFLite / ONNX 转换来的算子图。
GGUF 里的 GGML 图（自定义量化、RoPE 变体、GQA 等）
没有到 NNAPI 算子集的映射路径，且 llama.cpp 上游已移除 NNAPI 后端。

→ llama.cpp 与 NPU 之间不存在通路。
  要用 NPU 必须换模型格式与推理框架（LiteRT / LiteRT-LM 的 MTK delegate），
  而 MediaTek 公开侧只给 NP Converter 与 TFLite Shim API，
  完整 NPU runtime 要签 NDA。
```

### 8.4 GPU 为什么慢：硬件能力清单

`ggml_vulkan` 报告的 Mali-G615 MC6 能力：

```text
ggml_vulkan: 0 = Mali-G615 MC6 | uma: 1 | fp16: 1 | bf16: 0 | fp4: 0
              warp size: 16 | shared memory: 32768
              int dot: 0 | matrix cores: none
```

三个致命项，直接解释了性能差距：

```text
int dot: 0           不支持整数点积指令
                     Q4_K_M 这类量化的推理核心就是整数点积，
                     没有硬件指令只能退化到通用 ALU 模拟 → 这是最大瓶颈

matrix cores: none   不支持 KHR cooperative matrix，
                     matmul 用不上张量核心

bf16: 0              不支持 bfloat16
```

### 8.5 关于绝对值的一个必须说明

**本节的 CPU 数值高于第三节的详表数值，同一个参数下差了 50%：**

```text
              第三节详表      本节同参数      差异
1.5B pp128      18.44          27.60        +49.7%
1.5B tg64       14.55          18.46        +26.9%
0.6B pp128      49.44          72.75        +47.1%
```

原因是我没控制住一个变量：**机器的调频状态在漂移。**

```text
之前采样：cpu4 锁 1800 MHz，cpu7 锁 1800 MHz
本次采样：cpu4 到 2500 MHz，cpu7 到 2400 MHz

系统是 mtk-cpufreq-hw 硬件调频，请求来自厂商策略层。
它在不同时刻给出的频率档位不同（之前是 55~65% 上限，
这次接近 75%），导致同一参数的测量结果不稳定。
```

**这对本节的结论没有影响**，因为：

```text
本节所有后端测试是在**同一次会话内连续完成**的，
CPU 与 GPU 之间可以对比（相对关系可靠）。

跨节比较绝对值则不可靠——第三节与本节的 CPU 数字
就是同一参数下的两个不同结果。
```

**教训**：在这台机器上做后端对比，必须把 CPU 基线放在同一次会话里一起测，不能引用历史数据。这也是本次重新测一遍而不是直接引用旧 GPU 数据的原因。

## 九、测量方法说明（避免误读数据）

### 8.1 两种测量条件，绝对值不能混用

```text
条件甲  带预热（llama-bench 默认）+ -r 3
        1.5B pp512 = 22.42
        → 预热使 CPU 升频到位，接近"持续使用时的稳态"

条件乙  --no-warmup + -r 2
        1.5B pp512 = 18.40
        → 每次测量都是冷启，CPU 尚未升频，系统性偏低
```

本文档第三节表格用条件乙，3.2 节专门列了两者的对照。**不要跨条件比较绝对值。**

### 8.2 环境不干净会严重污染数据

曾出现这样的垃圾数据：

```text
pp512 = 3.68 ± 2.22
```

**标准差（2.22）大于均值（3.68）。** 原因是两个 `llama-bench` 进程同时在跑，互相抢内存与 CPU。

**判据：标准差超过均值的 10%，该组数据作废重测。**

### 8.3 频率采样是必备的交叉验证

每组测量前后都记录各核频率。若跑测期间频率明显低于上限且不随负载上升，说明数据被调频策略或热限制污染。本机情况是**恒定锁定在 55~65%**，属系统级限制而非热降频（温度仅 28~37°C）。

## 十、给使用者的参数建议

```text
模型选择
    追求回答质量      Qwen2.5-1.5B    首字 1.8 s   decode 12~15 t/s
    追求响应速度      Qwen3-0.6B      首字 0.4 s   decode 24~31 t/s

线程数
    -t 4    最优，不要改。加到 8 会让 decode 掉一半以上

上下文
    -c 2048 足够日常使用，更大只会增加内存占用与每步访存压力

GPU
    -ngl 0  必须显式指定。Mali-G615 实测 decode 慢 10~19 倍
            （ggml 报告 int dot: 0，量化推理无硬件加速）

实际命令
    llama-cli -m ~/models/Qwen3-0.6B-Q4_K_M.gguf -t 4 -c 2048
    llama-cli -m ~/models/qwen2.5-1.5b-instruct-q4_k_m.gguf -t 4 -c 2048
```

**体感优化的优先级**：

```text
1. 保持多轮对话，不要每次重贴背景
   命中提示词缓存能把首字延迟压到 1 秒内（1.5B）

2. 提问尽量简短
   512 token 的提示词在无缓存时要等 27.8 秒

3. 及时开新会话
   上下文到 1024 深度时 decode 已降 25%

4. 在意响应速度就换 0.6B
   首字延迟快 5 倍，这个差距比 decode 的 2.2 倍更影响手感
```

## 十一、待补项与已知局限

```text
仍缺的数据
    · 0.6B 的 pp1024 与 pp2048（1.5B 已完整）
    · 线程数 2、3、5、7 的精确值
      4/6/8 的对比已足以支撑「-t 4 最优」的结论

本次未做，属后续可做
    · 流式（stream: true）下的真实 TTFT
      当前用 max_tokens=1 的非流式请求近似，会有少量偏差
    · 持续压测下的热降频曲线
      上一台华为在压测中从 22.62 掉到 5.56 t/s，这台表现未测
    · 提示词缓存的量化收益
      目前只有两个样本点（0 vs 31 cached tokens），
      值得做一条"缓存命中比例 vs 首字延迟"的曲线

已知的数据污染因素
    · 部分测量期间后台有 llama-server 常驻进程
      空闲时几乎不占 CPU，但严格说构成背景干扰。
      表现为个别格的标准差偏大（如 0.6B pp128 的 ±2.70）
    · 调频策略把主频锁在 55~65%，所有绝对值都受影响
      这是系统级限制，Termux 无 root 改不了
```
