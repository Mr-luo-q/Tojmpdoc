# 0.6B / 1.5B 提速复现操作手册

对应判断、设备纠错与来源见 [手机小模型提速调研与复现.md](手机小模型提速调研与复现.md)。手机须已有Termux、两个GGUF与llama.cpp。本轮没有连接手机，以下手机命令和NDK构建是待执行协议；先跑最小基线，确认本机版本接受参数，再扩展。

## 准备与最小基线

```text
电脑确认设备 → 推送两个测量程序 → 手机核对环境
  → 停止正在运行的推理服务 → 只测0.6B基线
  → 基线成功 → 测1.5B → 单变量矩阵
```

电脑PowerShell：脚本仅推到中转目录；`run-as`需要当前Termux构建允许调试。若报 `package not debuggable`，改为把文件放入Download，在Termux授予存储权限后自己复制，不能声称run-as路径普遍可用。

```powershell

tools/platform-tools/adb.exe shell run-as com.termux cp /data/local/tmp/phone-speed-bench.py /data/data/com.termux/files/home/scripts/phone-speed-bench.py
tools/platform-tools/adb.exe shell run-as com.termux cp /data/local/tmp/measure-phone-stream.py /data/data/com.termux/files/home/scripts/measure-phone-stream.py
```

手机Termux执行。`pkg install`只在缺少依赖时运行，**先留环境记录再升级包**；升级后的结果应作为另一版本。


## 线程、批大小、Flash Attention与KV实验

先运行dry-run查看完整调用数，选择单一suite。每个候选都有ABBA顺序，不按“所有A先跑完再跑所有B”的方式比较。

```bash
# 线程实验模块：先一块筛选，再对收益候选做持续服务验证。
python ~/scripts/phone-speed-bench.py \
  --models ~/models/Qwen3-0.6B-Q4_K_M.gguf \
  --suite threads --out ~/speed-results/06-threads --dry-run

python ~/scripts/phone-speed-bench.py \
  --models ~/models/Qwen3-0.6B-Q4_K_M.gguf \
  --suite threads --out ~/speed-results/06-threads \
  --label standard-unplugged-no-fan

# 注意力实验模块：先d0检查支持，再独立测d2048，避免首次就跑完整长矩阵。
python ~/scripts/phone-speed-bench.py \
  --models ~/models/Qwen3-0.6B-Q4_K_M.gguf \
  --suite attention --depths 0 --out ~/speed-results/06-attention-d0

python ~/scripts/phone-speed-bench.py \
  --models ~/models/Qwen3-0.6B-Q4_K_M.gguf \
  --suite attention --depths 2048 --out ~/speed-results/06-attention-d2048

# 批大小实验模块：pp512使ub64/128/256/512的比较有实际区分。
python ~/scripts/phone-speed-bench.py \
  --models ~/models/Qwen3-0.6B-Q4_K_M.gguf \
  --suite batch --prompt 512 --out ~/speed-results/06-batch

# 重排实验模块：只能在确实编入CPU重排的构建上解释此开关。
python ~/scripts/phone-speed-bench.py \
  --models ~/models/Qwen3-0.6B-Q4_K_M.gguf \
  --suite repack --out ~/speed-results/06-repack
```

1.5B用同样suite，替换模型路径和输出目录为 `15-*`。`--blocks 3`用于复验，耗时也约为单块三倍。深度填充不计入tg的计时指标，但每个调用仍要付出填充时间，重复深度测试容易让手机热状态变化，应结合频率原文和可用热状态检查。

手工亲和性对照和真实“先处理后生成”负载：

```bash

llama-bench -m ~/models/Qwen3-0.6B-Q4_K_M.gguf \
```

## 实验服务、中文首字与缓存

使用独立端口8081、前台服务并保留完整日志。不会调用日常启动器，避免其中默认模型、UI和并发配置干扰。提示词素材在 [phone-prompts/](phone-prompts/README.md)：`问答.txt` 用于chat延迟，`缓存512.txt` 与 `缓存2048.txt` 用于裸completion缓存对照。经文件推送而不是 `adb shell` 传参，避开shell编码破坏中文。

手机Termux的服务终端：

```bash
# 服务模块：生成线程t与prefill线程tb分别固定；先用相同值建立基线。
llama-server -m ~/models/Qwen3-0.6B-Q4_K_M.gguf \
  -t 4 -tb 4 -c 4096 -b 512 -ub 128 \
  -ngl 0 --device none --no-kv-offload --no-op-offload \
  -fa off -ctk f16 -ctv f16 \
  --jinja --reasoning off --parallel 1 --metrics \
  --host 127.0.0.1 --port 8081 \
  2>&1 | tee ~/speed-environment/server-06.log
```

先Ctrl+C停止该服务，换 `-tb 6` 或 `-tb 8`，同题复测；t固定4，其他参数不变。选择FA/KV候选时同样先停止自己的实验服务，再分别替换 `-fa on` 和缓存类型；检查实际日志接受的设置。1.5B替换模型路径，并用独立日志名。

另一Termux终端执行：

```bash
# 首字模块：首轮与后续轮次分开分析，不把服务热缓存计入冷首字。
python ~/scripts/measure-phone-stream.py \
  --base-url http://127.0.0.1:8081 --expected-model Qwen3-0.6B \
  --prompt-file ~/prompts/问答.txt --endpoint chat \
  --max-tokens 128 --repeat 5 --out ~/stream-results/06-chat

# 缓存模块：裸completion用于可控前缀缓存对比，不用于聊天质量排名。
python ~/scripts/measure-phone-stream.py \
  --base-url http://127.0.0.1:8081 --expected-model Qwen3-0.6B \
  --prompt-file ~/prompts/缓存.txt --endpoint completion \
  --cache off --repeat 5 --out ~/stream-results/06-cache-off

python ~/scripts/measure-phone-stream.py \
  --base-url http://127.0.0.1:8081 --expected-model Qwen3-0.6B \
  --prompt-file ~/prompts/缓存.txt --endpoint completion \
  --cache on --repeat 5 --out ~/stream-results/06-cache-on
```

缓存on组应从新启动服务开始，第一轮填充、后四轮才作为热前缀请求。off/on组更换顺序复测。若没有cached_tokens字段，查看保存的prompt_n、服务slot日志和首字时间，不能直接填“命中”。想模拟固定系统背景加不同问题，应把背景放在最前面，再固定后缀变更位置；每次在最前面插时间戳/随机ID会破坏前缀。缓存只省已处理前缀的prefill，不消除decode访问历史KV的成本。

真正冷首字需重启实验服务并等健康检查完成，每次只发一个同题请求，至少5个独立启动。服务加载时间另计“启动→health就绪”，不要与常驻服务TTFT混写。本工具repeat5会复用同一服务，不能当作5次冷启动。

电脑测USB连接条件可用 `tools/platform-tools/adb.exe forward tcp:8081 tcp:8081`，在电脑运行同一个Python脚本。拔线后转发失效，电池测试应在手机本机运行；不要把USB测试记成“未充电”。

## CPU内核的隔离构建

优先在电脑通过Android NDK交叉编译，避免旧Termux的libc++ ABI问题。本例在PowerShell执行，需要Git、CMake、Ninja及 **NDK r28b（28.1.13356709）** 已安装；NDK不是本轮实际安装/构建过的依赖。若选别的版本，记录确切版本，不能把更换工具链的收益归于内核。源码位置用英文路径，输出保持在实验目录，不覆盖Termux包。

```powershell
# 构建取证模块：相同源码，使用不同目录产出三种CPU构建。
$speedNdk = "$env:LOCALAPPDATA/Android/Sdk/ndk/28.1.13356709"
Test-Path "$speedNdk/build/cmake/android.toolchain.cmake"
git clone https://github.com/ggml-org/llama.cpp.git D:/llama-speed-src
git -C D:/llama-speed-src checkout 091b6a7fc561b78da90a0ed2d524ec995458c657

# 通用CPU构建模块：这是同提交的受控基线。
cmake -S D:/llama-speed-src -B D:/llama-speed-build/generic -G Ninja `
  "-DCMAKE_TOOLCHAIN_FILE=$speedNdk/build/cmake/android.toolchain.cmake" `
  -DANDROID_ABI=arm64-v8a -DANDROID_PLATFORM=android-28 -DANDROID_STL=c++_static `
  -DCMAKE_BUILD_TYPE=Release -DBUILD_SHARED_LIBS=OFF `
  -DGGML_NATIVE=OFF -DGGML_BACKEND_DL=OFF -DGGML_CPU_ALL_VARIANTS=OFF `
  -DGGML_CPU_ARM_ARCH=armv8-a -DGGML_CPU_KLEIDIAI=OFF -DGGML_CPU_REPACK=ON `
  -DGGML_OPENMP=OFF -DGGML_VULKAN=OFF -DGGML_OPENCL=OFF `
  -DLLAMA_OPENSSL=OFF -DLLAMA_BUILD_TESTS=OFF
cmake --build D:/llama-speed-build/generic --target llama-bench llama-server llama-quantize -j 4

# i8mm构建模块：目标特性由K70E日志确认；该产物不要直接套用其他手机。
cmake -S D:/llama-speed-src -B D:/llama-speed-build/i8mm -G Ninja `
  "-DCMAKE_TOOLCHAIN_FILE=$speedNdk/build/cmake/android.toolchain.cmake" `
  -DANDROID_ABI=arm64-v8a -DANDROID_PLATFORM=android-28 -DANDROID_STL=c++_static `
  -DCMAKE_BUILD_TYPE=Release -DBUILD_SHARED_LIBS=OFF `
  -DGGML_NATIVE=OFF -DGGML_BACKEND_DL=OFF -DGGML_CPU_ALL_VARIANTS=OFF `
  "-DGGML_CPU_ARM_ARCH=armv8.6-a+dotprod+i8mm+fp16" `
  -DGGML_CPU_KLEIDIAI=OFF -DGGML_CPU_REPACK=ON `
  -DGGML_OPENMP=OFF -DGGML_VULKAN=OFF -DGGML_OPENCL=OFF `
  -DLLAMA_OPENSSL=OFF -DLLAMA_BUILD_TESTS=OFF
cmake --build D:/llama-speed-build/i8mm --target llama-bench llama-server llama-quantize -j 4

# KleidiAI构建模块：使用相同i8mm目标，仅打开优化内核库。
cmake -S D:/llama-speed-src -B D:/llama-speed-build/kleidi -G Ninja `
  "-DCMAKE_TOOLCHAIN_FILE=$speedNdk/build/cmake/android.toolchain.cmake" `
  -DANDROID_ABI=arm64-v8a -DANDROID_PLATFORM=android-28 -DANDROID_STL=c++_static `
  -DCMAKE_BUILD_TYPE=Release -DBUILD_SHARED_LIBS=OFF `
  -DGGML_NATIVE=OFF -DGGML_BACKEND_DL=OFF -DGGML_CPU_ALL_VARIANTS=OFF `
  "-DGGML_CPU_ARM_ARCH=armv8.6-a+dotprod+i8mm+fp16" `
  -DGGML_CPU_KLEIDIAI=ON -DGGML_CPU_REPACK=ON `
  -DGGML_OPENMP=OFF -DGGML_VULKAN=OFF -DGGML_OPENCL=OFF `
  -DLLAMA_OPENSSL=OFF -DLLAMA_BUILD_TESTS=OFF
cmake --build D:/llama-speed-build/kleidi --target llama-bench llama-server llama-quantize -j 4
```

逐个检查CMake退出码和“unused variable”提示。固定提交的KleidiAI依赖为v1.31.0 [S04]，配置阶段会下载它；网络失败属于构建失败。把每个目录的 `CMakeCache.txt`、`compile_commands.json`（若启用导出）、`build.ninja`、NDK `source.properties` 和构建日志留在结果归档，并配一份构建记录MD解释来源与选项。核对编译命令确实包含目标 `-march`；缺乏这一证据不能仅凭CPU Features说“已吃满i8mm”。

```powershell
# 部署模块：只推新文件到各自目录，不覆盖已经工作的运行时。
tools/platform-tools/adb.exe push D:/llama-speed-build/generic/bin/llama-bench /data/local/tmp/bench-generic
tools/platform-tools/adb.exe push D:/llama-speed-build/i8mm/bin/llama-bench /data/local/tmp/bench-i8mm
tools/platform-tools/adb.exe push D:/llama-speed-build/kleidi/bin/llama-bench /data/local/tmp/bench-kleidi
```

通过前面的run-as中转方法拷入 `~/speed-bin/`，在Termux给执行权限。用相同baseline命令更换 `--bench ~/speed-bin/bench-generic`、`bench-i8mm`、`bench-kleidi`，按 generic→i8mm→i8mm→generic，以及 i8mm→kleidi→kleidi→i8mm 次序执行。各次用不同结果目录并记录电源/热状态。只比较Termux包和新版优化包会把版本升级与内核优化混在一起。

若静态配置仍产生动态依赖，先用NDK的 `llvm-readelf -d` 检查DT_NEEDED，按匹配构建一并部署；不要复制vendor/system基础库填坑。若设备报illegal instruction，停止使用该产物并重新核对架构特性。测试程序用Termux应用身份运行；adb shell身份得到的调度速度另归为shell实验。

## 权重量化与其他框架的小规模验证

权重量化候选必须来自同一原始BF16/F16检查点；**不要把已有Q4_K_M再量化成Q4_0，称为标准精度对照**。在电脑使用同提交转换器生成F16 GGUF，再量化为Q4_K_M、Q4_0、可选Q3_K_M和Q8_0，记录原始HF revision、转换依赖和SHA-256。下方命令的模型源目录是已下载的完整原始权重，不是仓库现有量化文件。

```powershell
# 量化模块：先装固定源码要求的转换依赖，再对同一个F16输入量化。
python -m venv D:/llama-speed-convert-env
D:/llama-speed-convert-env/Scripts/python.exe -m pip install -r D:/llama-speed-src/requirements.txt
D:/llama-speed-convert-env/Scripts/python.exe D:/llama-speed-src/convert_hf_to_gguf.py `
  D:/model-sources/Qwen3-0.6B --outfile D:/model-candidates/qwen3-06-f16.gguf --outtype f16
# 电脑须另编同提交的host版llama-quantize；Android版不能在Windows执行。
D:/llama-speed-host/bin/Release/llama-quantize.exe D:/model-candidates/qwen3-06-f16.gguf D:/model-candidates/qwen3-06-q4_k_m.gguf Q4_K_M
D:/llama-speed-host/bin/Release/llama-quantize.exe D:/model-candidates/qwen3-06-f16.gguf D:/model-candidates/qwen3-06-q4_0.gguf Q4_0
```

host版生成前在Visual Studio开发者PowerShell中执行 `cmake -S D:/llama-speed-src -B D:/llama-speed-host -DLLAMA_OPENSSL=OFF` 和 `cmake --build D:/llama-speed-host --config Release --target llama-quantize`。若使用Ninja单配置，二进制位于 `bin/`，应以实际生成位置为准。转换依赖固定源码requirements只是最低版本约束，成功后还要保存 `pip freeze`；它并非锁定全部传递依赖的lock文件。

MNN是第三轮验证。先固定源码提交，再按S24当前说明从原始HF目录导出；导出器、转换器和手机runtime应来自同一版本，避免新C4融合模型配旧runtime。电脑导出示例：

```bash
# MNN导出模块：以下在已按官方要求安装导出依赖和MNNConvert的环境执行。
cd MNN/transformers/llm/export
python llmexport.py --path /path/to/Qwen3-0.6B \
  --export mnn --quant_bit 4 --quant_block 64 \
  --mnnconvert /path/to/MNNConvert --dst_path /path/to/mnn-qwen3-06
```

将完整输出模型目录和同版Android运行库/`llm_bench`传入新目录。在runtime `config.json`中设置CPU、thread_num4、precision low；对应 `config.md` 记录全部数据字段、模型源revision和哈希。MNNOpenCL单独作为另一个后端，不把高通Hexagon教程套到MediaTek。

```bash
# MNN基准模块：这是MNN自己的参数协议，不能替换成llama-bench参数。
./llm_bench -m ./mnn-qwen3-06/config.json -a cpu,opencl -t 4 -pg 128,64 -rep 3
```

先跑CPU、核对中文答案，然后确认OpenCL确实枚举Mali再测GPU；用同语义的组合负载与前面的llama `-pg 128,64` 比较，独立pp/tg行也应单独标注。MLC遵循归档S10的“权重转换→model library→Android APK”流程，涉及NDK/JDK/TVM和model package配置，当前没有现成的K70E受控资产，不把只安装APK算成性能复现。ExecuTorch/LiteRT-LM的格式与delegate门槛见主报告，先确认对应Qwen完整资产再投入转换。

## 固定题集、结果归档与判定

把每题保存为UTF-8独立 `.txt`，无需通过shell拼JSON。`问答.txt`可先用第1题。质量验证通过chat端点执行，每题保留完整答案；裸completion用于缓存实验，不能混进聊天评分。

| 题号 | 提示词原文 | 必须保持的条件 |
|---|---|---|
| 1 | 只输出JSON，不要代码框。张三买了3个单价12元的杯子，又付了5元运费。输出字段total和currency，currency固定为CNY。 | 合法JSON；total=41；currency=CNY；无多余文本 |
| 2 | 提取订单信息，只输出JSON。原文：订单号A102，收件人李华，电话13800138000，商品蓝色杯子2个。字段order_id、name、phone、item、quantity。 | 字符与数量正确，电话保留为字符串 |
