# 手机 llama.cpp 投机解码实测 · Redmi K70E

## 一、结论

字面上的“0.6B 草稿 + 2B 目标”在这台手机上跑不起来：Qwen3-0.6B 的词表是 151936，Qwen3.5-2B 是 248320，llama.cpp 要求两个模型词表差不超过 128，启动时直接拒绝。

换成同词表的两组最接近配置，实测全部比基线慢：

| 组合 | 提示 | 基线 | 投机解码 | 接受率 | 结果 |
|---|---|---:|---:|---:|---|
| Qwen3-0.6B → Qwen3-1.7B | 自然问答 | 16.93 | 8.84 | 50.0% | 慢 1.92 倍 |
| Qwen3-0.6B → Qwen3-1.7B | 逐字复述 | 15.77 | 9.85 | 77.8% | 慢 1.60 倍 |
| Qwen3.5-0.8B → Qwen3.5-2B | 自然问答 | 13.88 | 9.44 | 9.1% | 慢 1.47 倍 |

关键点不是接受率。逐字复述已经到 77.8%，仍然只有 9.85 t/s，说明每轮草稿加验证的固定开销太大，多接受的 token 补不回来。在这台 4 线程手机上，llama.cpp 这版 draft 投机解码没有可用收益。

## 二、环境与口径

| 项 | 值 |
|---|---|
| 手机 | Redmi K70E，型号 2311DRK48C，duchamp |
| 系统 | Android 16，11.6 GB 内存 |
| 运行时 | Termux 官方 llama.cpp 0.6.0（build 0），Clang 21 编译，aarch64 |
| 线程 | `-t 4`，与之前单模型实测的最优线程数一致 |
| 采样 | `--temp 0` 贪心，`-c 2048` |
| 生成长度 | 48 token |
| 电池温度 | 测试前 25.1°C，测试后 33.4°C，电量 95% |

模型都在 `~/models`：

```text
Qwen3-0.6B-Q4_K_M.gguf        378 MB   词表 151936
Qwen3-1.7B-Q4_K_M.gguf        1.0 GB   词表 151936
Qwen3.5-0.8B-Q4_K_M.gguf      508 MB   词表 248320
Qwen3.5-2B-Q4_K_M.gguf        1.1 GB   词表 248320
```

基线用 `llama-cli -st` 单轮对话，投机用 `llama-speculative`，两者都会套 Qwen 的聊天模板。每条配置跑 3 次，基线与投机交替执行，每次间隔 2–3 秒，减少顺序偏差。

## 三、字面组合为什么失败

直接启动 Qwen3-0.6B 草稿 + Qwen3.5-2B 目标：

```text
draft model vocab must closely match target model to use speculation but
target vocab size 248320 does not match draft vocab size 151936
- difference 96384, max allowed 128
```

投机解码要在同一套 token id 上比较草稿和目标的概率，词表不同就无法验证。Qwen3 与 Qwen3.5 是两代 tokenizer，不能混搭。同代里能配的组合只有：

```text
Qwen3 代：   Qwen3-0.6B 草稿  → Qwen3-1.7B 目标
Qwen3.5 代： Qwen3.5-0.8B 草稿 → Qwen3.5-2B 目标
```

没有 Qwen3.5-0.6B，所以“0.6B + 2B”若坚持同词表，只能是 0.6B + 1.7B。

## 四、Qwen3-0.6B → Qwen3-1.7B

三次原始数据：

| 提示 | 模式 | 第1次 | 第2次 | 第3次 | 均值 | 接受率 |
|---|---|---:|---:|---:|---:|---:|
| 自然问答 | 基线 | 17.9 | 17.0 | 15.9 | 16.93 | — |
| 自然问答 | 草稿长度 1 | 9.18 | 8.93 | 8.40 | 8.84 | 50.0% |
| 逐字复述 | 基线 | 16.3 | 15.6 | 15.4 | 15.77 | — |
| 逐字复述 | 草稿长度 1 | 10.12 | 9.77 | 9.67 | 9.85 | 77.8% |
| 逐字复述 | 草稿长度 2 | 10.17 | 9.58 | 9.58 | 9.78 | 75.0% |

草稿长度扫描（自然问答，32 token，单次）：

| 草稿长度 | 1 | 2 | 3 | 4 | 6 |
|---|---:|---:|---:|---:|---:|
| 速度 t/s | 9.53 | 7.88 | 6.83 | 5.53 | 4.55 |
| 接受率 | 52.4% | 38.9% | 33.3% | 25.0% | 21.4% |

草稿越长越慢：多出的草稿 token 大多被拒绝，但每个都要跑一次 0.6B 前向，验证批次也跟着变长。最优的草稿长度是 1，仍然只有基线的一半左右。

## 五、Qwen3.5-0.8B → Qwen3.5-2B

| 模式 | 第1次 | 第2次 | 第3次 | 均值 | 接受率 |
|---|---:|---:|---:|---:|---:|
| 基线 | 14.83 | 13.4 | 13.4 | 13.88 | — |
| 草稿长度 1 | 10.02 | 9.15 | 9.14 | 9.44 | 9.1% |

2B 目标的单 token 成本更高，本来更适合用草稿摊薄，但 0.8B 草稿与 2B 目标的输出分布差得太远，接受率只有 9.1%。每轮基本只接受 0 到 1 个草稿，草稿模型的 29 ms/token 全是净开销。

## 六、服务端交叉验证

用 `llama-server` 走同一套投机实现，结果方向一致，甚至更差：

| 配置 | 提示 | 速度 t/s | 说明 |
|---|---|---:|---|
| 1.7B 基线 | 逐字复述 | 17.37 | 无投机 |
| 1.7B + 0.6B，草稿长度 2 | 逐字复述 | 6.46 | 接受 31/63 = 49.2% |
| 1.7B + ngram-simple 默认参数 | 逐字复述 | 17.05 | 基本无变化 |
| 1.7B + ngram-simple，n=4/m=16 | 逐字复述 | 12.78 | 13 个草稿，0 接受 |

`llama-server` 的 draft 路径比命令行还慢，说明不是 `llama-speculative` 这个示例独有的问题，而是这版 llama.cpp 在 4 线程 ARM CPU 上的验证路径没有把批量优势做出来。

## 七、怎么解释“接受率高但仍然慢”

以逐字复述、草稿长度 1 为例：

```text
基线：      每 token 约 63 ms
投机：      均值 9.85 t/s ≈ 102 ms/token
接受率：    77.8%
```

如果验证 2 个 token 的成本接近 1.2 个单 token，理论上每轮约 `23 ms 草稿 + 66 ms 验证 = 89 ms`，能产出 `1 + 0.778 = 1.78` 个 token，折合约 20 t/s，应该比基线快。实际只有 9.85 t/s，说明每轮真实成本约 102 × 1.78 ≈ 181 ms，验证批次的开销远高于一次普通 decode。

草稿模型本身也不便宜：0.6B 在手机上单 token 约 23 ms，已经接近 1.7B 单 token 63 ms 的三分之一。只要验证环节不能把多个候选压成接近一次前向，草稿就一定是净亏。

温度也在拖后腿：三次基线从 17.9 掉到 15.4，电池从 25.1°C 升到 33.4°C。但首轮最有利的对比仍是 17.9 对 9.18，差距不是热衰减造成的。

## 八、复现命令

基线：

```bash
llama-cli -m ~/models/Qwen3-1.7B-Q4_K_M.gguf \
  -p "用三句话解释什么是模型量化。" -n 48 -t 4 --temp 0 -c 2048 -st
```

投机：

```bash
llama-speculative -m ~/models/Qwen3-1.7B-Q4_K_M.gguf \
  -md ~/models/Qwen3-0.6B-Q4_K_M.gguf \
  -f ~/spec-bench/natural.txt -n 48 -t 4 --temp 0 -c 2048 \
  --spec-draft-n-max 1
```

字面组合的失败可以这样复现：

```bash
llama-speculative -m ~/models/Qwen3.5-2B-Q4_K_M.gguf \
  -md ~/models/Qwen3-0.6B-Q4_K_M.gguf -n 8 -t 4
```

## 九、下一步

draft 投机解码不适合作为这台手机的默认路径。更值得试的是不加载第二个模型的 n-gram / lookahead 方案，它对模板化、复述类文本没有草稿模型的前向成本；MNN 的 lookahead 在电脑上已经验证过 +95%，手机上还没做同口径对照。

如果一定要继续 llama 路线，需要同时满足三个条件才可能翻盘：草稿模型明显更小（例如 0.3B 级）、与目标严格同词表、运行时能把验证批次压到接近单 token 成本。当前这版 llama.cpp 在 K70E 上第三条不成立，换草稿大小也救不回来。
