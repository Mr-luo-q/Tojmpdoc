# 端侧推理优化与容器化调研

调研日期：2026-10-03
设备：华为 Pura 70 Pro+（HBN-AL80），Kirin 9010，Android 12，16 GB
已有部署：llama.cpp b11146（Android arm64 预编译），Qwen2.5-1.5B / Qwen3-0.6B

本报告回答两个问题：一是剪枝等端侧推理优化方法能否让这台手机跑得更快；二是能否在手机上部署 Docker 容器。

---

## 第一部分 · 剪枝与模型压缩

### 1.1 剪枝要解决什么

深度网络训练完成后存在大量冗余权重。剪枝就是按某种重要性判据把不重要的权重或结构去掉，
用更稀疏或更小的模型换回相近性能。

它属于「从大模型得到小模型」的三条主流路径之一。三条路径的定位不同：

```text
从 LLM 得到 SLM（小语言模型）
│
├─ 剪枝 Pruning              删掉参数        → 减小体积与计算量
├─ 知识蒸馏 Distillation     大模型教小模型   → 重新训练出一个更小的模型
└─ 量化 Quantization         降低参数精度     → 减小体积，硬件原语直接支持
```

### 1.2 两大分支及各自代价

```text
剪枝
│
├─ 非结构化剪枝 unstructured（按单个权重删）
│    判据：权重绝对值 |W|，或权重与激活的联合指标
│    代表：SparseGPT、Wanda
│    优点：同等稀疏度下精度损失小
│    代价：权重矩阵变成不规则稀疏，内存访问模式被打乱
│          → 需要专门的稀疏 kernel，通用硬件上拿不到加速
│
└─ 结构化剪枝 structured（按整块删）
     判据：整层 / 整个注意力头 / 整个通道的重要性
     代表：ShortGPT、LLM Pruner
     优点：直接降低矩阵维度，不需要特殊硬件就能真加速
     代价：同等压缩率下精度掉得比非结构化多
```

### 1.3 两个代表方法的具体判据

**SparseGPT**（Frantar & Alistarh, 2023）把剪枝形式化为逐层的稀疏回归问题，用一个稀疏求解器
决定删除哪些权重，同时补偿剩余权重以最小化重建误差。可在 OPT-175B、BLOOM-176B 这类
大规模模型上做到最高 60% 稀疏度而无需重新训练。

**Wanda**（Sun et al., 2024）大幅简化了这件事。它的判据是：

```text
重要性(权重 w_ij) = |w_ij| × ‖该权重对应的输入激活 X_j‖
```

把「权重本身有多大」和「这个输入通道实际有多活跃」相乘。好处是只需一次前向传播、
不需要重新训练、也不需要求解回归。

**两者都依赖校准数据**来估计输入统计量 —— 这一点容易被忽略：剪枝不是纯静态操作，
它假设你喂进去的样本能代表实际输入分布。校准数据选得不好，剪枝后的质量会明显下降。

### 1.4 核心原理：剪枝减少乘加次数，不减少字节流量

这是本报告最重要的结论，它决定了剪枝能否用于本机。

decode 阶段每生成一个 token，必须把全部权重从内存完整读一遍，属于内存带宽受限：

```text
剪枝做了什么
    把部分权重置零 → 计算时跳过这些乘加 → 减少的是 FLOPs

剪枝没做什么
    零权重仍然占着内存位置 → 需要读的字节数没有变
```

对比各种手段的真实效果：

| 手段 | 减少字节流量 | 通用硬件真加速 | 前提 |
|---|---|---|---|
| int4 量化 | 是，权重体积降到 1/4 | 是 | 无特殊要求 |
| 结构化剪枝 | 是（维度真的变小） | 是，但精度损失较大 | 无特殊要求 |
| 非结构化剪枝 | **否** | 通常否 | 需要硬件级稀疏加速 |
| 稀疏 kernel | 是 | 是 | 需要专门的稀疏计算库 |

**关键前提：** llama.cpp 在 Android 上的 CPU 后端没有可用的稀疏 kernel。
因此即使拿到一个 50% 稀疏的模型，在手机上也不会更快 —— 瓶颈在内存带宽，剪枝没有改动它。

### 1.5 与本机实测数据的一致性检验

本机实测（详见 `提速调研报告.md`）：

```text
1.5B Q4_K_M   体积 1.04 GB   decode 18~22 t/s
0.6B Q4_K_M   体积 0.38 GB   decode 49~52 t/s      快约 2.4 倍
```

0.6B 更快的原因是**权重体积真的只有 34%**，与访存公式 `速度 ≈ 带宽 ÷ 体积` 一致。
这不是任何稀疏技术带来的收益，而是「换了一个训练时就更小的模型」。

反推有效带宽：`1.117 GB ÷ (1/22.62 t/s) ≈ 25.3 GB/s`，为理论值 68.2 GB/s 的 37%。

### 1.6 结论：剪枝对这个场景不是正确工具

```text
想提高生成速度，只有两条路
│
├─ 路 1：减小「实际占用的字节数」        有效
│    ├─ 换更小的模型      0.6B vs 1.5B → 已实测 2.4 倍
│    ├─ 更低比特量化      Q4 → Q3/Q2   → 有收益但质量掉得快
│    └─ 结构化剪枝        真降维度      → 需专门工具链，收益不如直接换模型
│
└─ 路 2：提高「有效带宽」                硬件决定，软件无解
     ├─ 更大内存带宽      换机器
     └─ 提高带宽利用率    已到 37%，余量有限
```

直接选用训练时就更小的模型（如 Qwen3-0.6B），质量与速度的权衡优于把 1.5B 剪到 0.6B。
后者还要自行完成校准、剪枝、评估三步，且拿不到推理加速。

## 第二部分 · 手机部署 Docker 容器

### 2.1 结论先行

**无 root 装不了真正的 Docker，而且即使 root 也未必能跑。** 这不是配置问题，是内核层面的限制。

### 2.2 机制：为什么 daemon 起不来

Docker 分成两半，混淆这两者是「手机能不能跑 Docker」这个问题含糊不清的根源：

```text
docker（客户端）
    普通程序，通过 HTTP 和 daemon 通信
    不需要任何权限 → 手机上完全可用

dockerd（守护进程）
    真正创建容器的那一半，启动时需要三件事：
      ① 创建 namespace（PID / mount / network / user）
      ② 写 cgroup（runc 用它限制容器的 CPU 与内存）
      ③ 挂载 overlay 文件系统（分层镜像靠它拼装）
```

Termux 是普通 Android 应用，运行在自己的应用 UID 下，没有 `CAP_SYS_ADMIN`，
这三样一样都拿不到。

### 2.3 需要纠正的广泛误传

「Android 没有 namespace 和 cgroup」这个说法是**错的**。

Android 本身就是 Linux，它大量使用 cgroup 来管理应用的 CPU 和内存。
真正的障碍是**访问权限**，不是功能缺失。实测时可以观察到 cgroup v2 控制器
（`cpuset cpu io memory hugetlb pids rdma`）清晰可见，但层级是只读的。

「看得见机器」和「被允许驾驶它」是两件不同的事。

### 2.4 为什么 root 也常常救不了

```text
原因 ① 版本陈旧
    Termux 的 docker 包只放在 root-repo（专供已 root 设备）
    版本被钉在 20.10.12，最后一次改动是 2021-12-05
    同期上游 Docker 已到 29.3.1 —— 相差四年半，中间所有 CVE 都在
    来源：termux/termux-root-packages

原因 ② 内核配置问题（更致命）
    即使真 root 跑起 daemon，runc 仍要往 cgroup 里放容器，
    而多数 Android 内核不暴露它需要的那套层级：
        mkdir /cpuset/docker: no such file or directory
    来源：termux-packages issue #15662（至今未关闭）

    这是设备内核构建的属性，没有哪个包能绕过，
    除非自行编译带相应选项的内核。
```

### 2.5 三条真正能走的路

| 方案 | 需 root | daemon 在手机上 | 需另一台服务器 | 日常可用性 |
|---|---|---|---|---|
| Docker CLI + 远程 daemon | 否 | 否 | 是 | 可以 |
| QEMU 虚拟机 | 否 | 是（guest 内） | 否 | 勉强，纯模拟开销 |
| termux root-repo 的 Docker | 是 | 是，前提内核配合 | 否 | 基本不行 |

**方案一 · 客户端指向远程 daemon。** 客户端不需要任何特权：

```bash
# 走 SSH（推荐，复用已有密钥）
export DOCKER_HOST=ssh://user@your-server
docker ps

# 或走 TLS + 客户端证书（必须是 2376，绝不能用明文的 2375）
export DOCKER_HOST=tcp://your-server:2376
export DOCKER_TLS_VERIFY=1
```

本机已有现成资源：`D:\项目\树莓派` 记录了一台正在跑 Home Assistant 容器的树莓派，
可以直接作为远程 daemon 的宿主。

**方案二 · QEMU。** 虚拟机自带内核，因此 guest 内部有真正的 namespace 和 cgroup，
特权在 guest 内行使，不需要手机 root。已有 `termux-qemu-docker` 的包请求在推进
（termux-packages issue #30165）。

代价是明确的：在手机 CPU 上模拟一台机器、占用约 1 GB 内存（而 Android 想回收它）、
设备持续发热。启动 Alpine 跑通 `hello-world` 是可行的演示，但**构建真实镜像的体验很差**，
属于演示而非工作流。

**方案三 · root-repo 的 Docker。** 需要 root，版本陈旧，且仍受内核cgroup 布局限制。

### 2.6 实际需要的往往是「干净的 Linux userland」

多数人搜「手机装 Docker」，真实需求是三者之一：隔离的环境、可复现的环境、
或者就是一个能正常 `apt install` 的真 Linux。这个在**无 root 条件下可以做到**。

```text
proot（做系统调用转译，不是真隔离，因此不需要特权）
│
└─ proot-distro（Termux 官方维护）
     ├─ 不需要 root
     ├─ 可安装完整 Ubuntu / Debian / Arch / Alpine 等发行版
     ├─ 内部 apt / pip 正常工作
     └─ 可跑 Python、编译工具链，甚至 PyTorch（CPU 版）

    不能做的：
     ├─ 真 Docker daemon（仍需要 overlayfs 挂载与 cgroup 写权限）
     └─ 需要 CAP_SYS_ADMIN 的操作（mount、改网络栈）
```

未经验证的第三方方案（仅见于搜索索引，未实测，不作为推荐）：
[Podroid](https://github.com/ExTV/Podroid)（无需 root 启动 Alpine 跑 Podman/Docker/LXC）、
[udockerd](https://pypi.org/project/udockerd/)（用户态 Docker 实现）。

### 2.7 实证：这套方案已经在本机跑起来了

本报告的 2.6 节当时是**文献推断**。之后在同一台手机上实际完成了部署，
推断得到验证，同时也收获了文献里没有的工程细节。

```text
目标        在手机上跑 Home Assistant
采用的路线  proot-distro 容器 + pip 安装 Home Assistant Core
结果        成功。HA Core 2026.2.3 运行在 Debian 13 容器内，
            HTTP 200 响应，日志零错误，进程 PPID=1 已脱离 adb 会话
```

对照本报告此前的判断：

| 此前的判断 | 实际结果 |
|---|---|
| Docker daemon 无 root 起不来 | **验证成立**。Docker Hub 亦不可达，连镜像都拉不到 |
| proot 能做到真 Linux userland | **验证成立**。Debian 13、apt、Python 3.13.5、pip 全部正常 |
| proot 不能跑真 Docker daemon | 未再尝试，无必要 —— 目标已用非 Docker 方式达成 |
| 需要 root | **不需要**，全程无 root |

补上文献里没提到的三个工程细节，它们比「能不能跑」更容易卡住人：

**① 容器内必须重置 PATH。** proot 会把 Termux 的 `PATH` 带进容器，
导致容器内的 `python3` 实际是 Termux 的 3.14.6 而非 Debian 的 3.13.5。
不重置会误判整个环境（我一度据此以为能装最新版 HA，实际不能）。
解法是在容器内执行时统一前置
`export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`。

**② proot 的 `--kill-on-exit` 让后台进程活不下来。** 这个选项会在 login 会话
退出时杀掉容器内所有进程。因此在**容器内部**用 `nohup` 或 `setsid` 双 fork
全部无效（实测日志连一行都没写出）。脱离动作必须发生在 **Termux 侧**，
把整个 `proot-distro login` 会话脱离：

```bash
setsid proot-distro login debian -- <容器内命令> > log 2>&1 < /dev/null &
```

**③ Docker Hub 不可达时如何装 rootfs。** proot-distro 5.x 默认从 Docker Hub
拉 OCI 镜像，国内常不通。它同时支持「本地 rootfs 压缩包」与「直接给 URL」两种模式，
所以可以从 `images.linuxcontainers.org` 取官方 `rootfs.tar.xz` 绕过：

```bash
proot-distro install ~/debian-rootfs.tar.xz --name debian
```

顺带一条判断经验：探测镜像源时 **HTTP 401 不等于不通**。401 说明服务端正常响应、
只是要求认证；`HTTP 000` 才是连 TCP 都没建立。本次实测 Docker Hub 全线 000，
而 `docker.m.daocloud.io`、`ghcr.io`、`quay.io` 都是 401（可用）。

完整的构建过程、六个坑的细节与验证记录见 [HomeAssistant构建文档.md](HomeAssistant构建文档.md)。

## 第三部分 · 待验证与未做的事

按 AGENTS.md 的要求，明确区分已验证与未验证。

**已验证的事实**

| 项目 | 依据 |
|---|---|
| decode 是内存带宽受限，非算力受限 | 本机实测：CPU 大核跑在 1.12~1.62GHz（上限 2.30GHz），未跑满却已达 37% 带宽 |
| 0.6B 比 1.5B 快约 2.4 倍，靠体积而非稀疏 | 本机实测，两轮顺序对调复现 |
| Docker daemon 在无 root 的 Termux 内无法启动 | 权威机制解释 + 两份一手 issue 记录 |
| Android 有 cgroup 但应用无权写 | 机制澄清，多方一致 |
| Termux 的 docker 包版本为 20.10.12（2021 年） | termux-root-packages 配方 |

**未验证 / 待确认**

```text
① 剪枝代码的实际运行与掉点评估
   本报告只做了原理与方法调研，没有在真机上跑过任何剪枝流程。
   基于 1.4 节的原理判断它对本机无用，但这是推论，不是实测。

② 本机内核的 namespace 与 cgroup 实际能力
   原计划实测（检查 /proc/self/ns/、cgroup.controllers、unshare 权限），
   但手机在操作前断开连接，未完成。报告中的相关结论来自文献而非本机实测。

③ proot-distro 在本机的实际表现
   未安装、未测试。是否可装、装完能跑到什么程度需要实测。

④ Podroid 与 udockerd
   只有搜索索引信息，抓取失败，未验证其可用性与安全性。

⑤ 半导体制冷背夹对持续性能的实际改善
   有第三方实测支持有效，本机无该设备，未验证。
```

**建议的下一步（需手机连接）**

```text
优先级 1  实测本机内核能力，确认第二部分结论
          检查 /proc/self/ns/、/sys/fs/cgroup/cgroup.controllers、unshare 权限
          这是一条命令的事，能把「文献结论」变成「本机事实」

优先级 2  安装 proot-distro 并实测边界
          pkg install proot-distro && proot-distro install ubuntu
          然后验证：能否 apt、能否 pip、能否跑 Python 科学计算栈

优先级 3  若确实需要 Docker，评估树莓派作为远程 daemon 的方案
          本机已有树莓派环境，无需新购设备
```
