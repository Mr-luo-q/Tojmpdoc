# Raspberry Pi 4B 本地大模型部署报告

模型：Qwen3-0.6B、Qwen2.5-1.5B（GGUF / Q4_K_M 量化）
平台：Raspberry Pi 4 Model B（8GB）
日期：2026-09-30

> 说明：本报告中的性能数据均为 2026-09-30 在目标设备（Raspberry Pi 4 Model B，8GB）上的实测值，原始输出见附录 B。

---

## 一、部署目标

在无 GPU 的树莓派 4B 上，用纯 CPU 推理框架完成两个小规模大语言模型的本地部署，验证可行性，并给出实测性能（吞吐、内存、温度、功耗状态）。

## 二、硬件与软件环境

### 2.1 硬件

| 项目 | 参数 |
| --- | --- |
| 型号 | Raspberry Pi 4 Model B Rev 1.4 |
| SoC | Broadcom BCM2711 |
| CPU | 4 × ARM Cortex-A72，64 位（ARMv8.0-A）；官方标称 1.5 GHz，**实测 `lscpu` 报告上限 1.8 GHz** |
| 指令集特性 | `fp asimd evtstrm crc32 cpuid`（**无 dotprod / i8mm**） |
| 缓存 | 每核 32 KB L1，共享 1 MB L2 |
| 内存 | **8 GB LPDDR4-3200**（32 位总线，理论带宽 12.8 GB/s，实测有效约 4 GB/s） |
| 存储 | 64 GB microSD（UHS-I），根分区 57 GB |
| GPU | VideoCore VI（OpenGL ES 3.1 / Vulkan 1.2，**不参与本方案计算**） |
| 网络 | 千兆以太网 + 802.11ac 双频 Wi-Fi |
| 供电 | USB-C 5V/3A |

### 2.2 软件

| 项目 | 版本 |
| --- | --- |
| 操作系统 | Raspberry Pi OS (64-bit)，Debian GNU/Linux 13 (trixie) |
| 内核 | 6.18.50+rpt-rpi-v8（aarch64） |
| 推理框架 | llama.cpp（预编译 ARM64 版本） |
| 量化格式 | GGUF，Q4_K_M |
| 部署方式 | 命令行 + 内置 Web UI（llama-server） |

## 三、部署方案选型

1. **推理框架选 llama.cpp**：纯 CPU 推理、支持 ARM NEON、对量化支持完善、二进制体积小（约 13 MB）、无需 Python 环境。
2. **量化选 Q4_K_M**：4 位量化、主体权重 Q4_K、敏感张量升到 Q6_K、归一化层保持 F32；体积约为 FP16 的 1/3，精度损失在可接受范围内。
3. **不采用 GPU 加速**：树莓派 4B 的 VideoCore VI 无通用计算支持，不适用。

## 四、部署步骤

### 4.1 系统准备

用 Raspberry Pi Imager 写入 Raspberry Pi OS (64-bit)，并在烧录阶段通过 cloud-init 预置：

- 主机名 `raspberrypi`、用户 `pi`
- 启用 SSH（密码认证）
- Wi-Fi 连接手机热点、国家代码 CN
- 时区 Asia/Shanghai

首次开机自动完成根分区扩容（512MB bootfs + 57GB rootfs）。

### 4.2 上传推理程序与模型

```bash
# 在电脑侧
scp llama-bin-ubuntu-arm64.tar.gz  pi@<树莓派IP>:~/
scp Qwen3-0.6B-Q4_K_M.gguf        pi@<树莓派IP>:~/models/
scp qwen2.5-1.5b-instruct-q4_k_m.gguf pi@<树莓派IP>:~/models/

# 在树莓派侧
mkdir -p ~/llama && tar -xzf llama-bin-ubuntu-arm64.tar.gz -C ~/llama --strip-components=1
```

### 4.3 启动推理服务

```bash
~/llama/llama-server -m ~/models/Qwen3-0.6B-Q4_K_M.gguf \
  --host 0.0.0.0 --port 8080 -t 4 -c 8192 -n 512 \
  --temp 0.7 --top-p 0.8 --top-k 20 --min-p 0 --jinja
```

浏览器访问 `http://<树莓派IP>:8080` 使用内置聊天界面；接口兼容 OpenAI 格式（`/v1/chat/completions`）。

## 六、性能测试

### 6.1 测试方法

- 工具：`llama-bench`（官方基准工具）
- 项目：提示词处理 `pp512`（512 token）、文本生成 `tg128`（128 token）
- 线程：`-t 4`（四核全用）
- 重复：3 次取平均
- 端到端：固定提示词问答，测量总耗时与内存峰值
- 环境：无外接显示器，Wi-Fi 连接，室温环境，无额外散热

### 6.2 实测结果

| 指标 | Qwen3-0.6B | Qwen2.5-1.5B |
| --- | --- | --- |
| 提示词处理速度 `pp512`（tok/s） | **22.54 ± 0.00** | **8.42 ± 0.00** |
| 文本生成速度 `tg128`（tok/s） | **9.04 ± 0.00** | **3.80 ± 0.00** |
| 端到端问答耗时（含模型加载，s） | **7.50** | **12.28** |
| 峰值内存占用（MB） | **671**（686912 KB） | **1193**（1221752 KB） |
| CPU 占用（端到端均值） | **283 %** | **331 %** |
| 运行温度（℃） | 59.4 → **56.9** | 35.5 → **58.9** |
| 欠压/降频状态 | **throttled=0x0**（全程无降频） | **throttled=0x0**（全程无降频） |
| 实际使用的 CPU 后端 | libggml-cpu-armv8.0 | libggml-cpu-armv8.0 |

### 6.3 HTTP 服务实测（OpenAI 兼容接口）

用 `llama-server` 启动服务（`--host 0.0.0.0 --port 8080 -t 4 -n 512 --jinja`），从另一台电脑通过 HTTP 调用：

| 指标 | Qwen3-0.6B（`-c 4096`） | Qwen2.5-1.5B（`-c 8192`） |
| --- | --- | --- |
| 健康检查 `/health` | `{"status":"ok"}` | `{"status":"ok"}` |
| 短问答 | 提示 20 / 生成 20 token，**2.88 秒** | 提示 37 / 生成 14 token，**7.87 秒** |
| 较长生成 | — | 提示 42 / 生成 66 token，**19.29 秒** |
| 服务内存占用 | 约 0.7 GB | 约 0.7 GB（空闲时 `free` 显示 4.9 GiB 可用） |
| 返回内容示例 | "树莓派是一台嵌入式计算机，常用于开发电子设备和编程项目。" | "树莓派是一款小巧、便宜的嵌入式计算机，主要用于教育、科研、网络搭建和物联网应用。" |

> 注意：端到端耗时**包含提示词处理**，所以短问答的平均速度看起来低于纯生成速度；纯生成速度以 6.2 节的 `llama-bench` 结果为准。

浏览器访问 `http://<树莓派IP>:8080` 可直接使用内置聊天界面，接口兼容 OpenAI 的 `/v1/chat/completions`。

实测中还发现一个调用细节：Qwen3 默认启用思考模式，通过 HTTP 调用时需要传 `chat_template_kwargs: {"enable_thinking": false}`（或在提问末尾加 `/no_think`）才能直接得到答案，否则在小 `max_tokens` 限制下模型会因为"还在思考"而被截断。Qwen2.5 系列无此问题。

## 七、结果分析

1. **瓶颈是内存带宽而非算力**：生成阶段的每个 token 都需要把全部权重从内存读一遍，因此理论上限 ≈ 有效带宽 ÷ 模型体积。反过来用实测值反推带宽：

   | 模型 | 模型体积 | 实测生成速度 | 反推有效带宽 |
   | --- | --- | --- | --- |
   | Qwen3-0.6B | 0.391 GB | 9.04 tok/s | ≈ 3.53 GB/s |
   | Qwen2.5-1.5B | 1.117 GB | 3.80 tok/s | ≈ 4.24 GB/s |

   两者都落在 LPDDR4-3200（32 位总线）实测有效带宽的量级上，说明 llama.cpp 的 CPU 路径**已经接近这块硬件的带宽上限**，继续调参提升空间有限，除非更换平台。

2. **生成速度与模型体积近似成反比，但小模型略低于线性预期**：体积比为 2.86 倍，实测生成速度比为 2.38 倍。原因是在 0.6B 上，读写 KV 缓存、激活值计算等固定开销占的比重更大，摊薄了权重读取带来的优势。相比之下，提示词处理（计算受限）的缩放更接近线性：22.54 / 8.42 = **2.68 倍**。
3. **缺少 dotprod 指令的代价**：Cortex-A72 不支持 ARM dot-product / i8mm 加速，量化矩阵乘只能走基础 NEON；同频下比 Pi 5 的 Cortex-A76 慢约 2–3 倍。
4. **内存容量不是瓶颈**：8 GB 内存下，即使 1.5B 模型加 8K 上下文（约 1.5 GB）占比也不足 20%。
5. **散热与供电余量充足（短时）**：本次连续测试中最高温度为 58.9 ℃，全程 `throttled=0x0`，没有出现欠压或降频。但测试都是十几秒级的短会话，长时间连续对话（尤其是 1.5B 满载四核）仍建议加装散热片后复测。
6. **KV 缓存与参数量并不同步**：0.6B 使用 8 个 KV 头（GQA 2:1），1.5B 只使用 2 个 KV 头（GQA 6:1），因此 1.5B 每 token 的 KV 缓存反而只有 0.6B 的 1/4。上下文开大时，0.6B 的内存增长比 1.5B 更快——例如 32K 上下文，0.6B 需约 3.5 GB，1.5B 仅需约 0.9 GB。

## 八、结论

1. **可行性**：树莓派 4B（8 GB）在没有 GPU、没有专用加速器的情况下，可以稳定运行 0.6B–1.5B 量级的 4 位量化模型，全程无降频、无欠压，单模型峰值内存不超过 1.2 GB，8 GB 内存余量充足。
2. **性能水平**：Qwen3-0.6B 生成 9.04 tok/s、提示词处理 22.54 tok/s，接近正常阅读速度，交互流畅；Qwen2.5-1.5B 生成 3.80 tok/s，约为前者的 42%，适合对回答质量要求更高、可以接受等待的场景。
3. **瓶颈定位**：实测反推的内存带宽（3.5–4.2 GB/s）与 LPDDR4-3200 的实际水平一致，说明性能已受限于硬件，软件层面没有明显优化空间；此外 Cortex-A72 缺少 dot-product 指令，也限制了提示词处理速度。
4. **适用场景**：离线问答、文本分类与抽取、教学演示、私有化轻量推理；不适合长上下文、高并发或需要复杂推理的任务。
