# 手机端部署 1.5B 大模型 · 项目总结

更新日期：2026-10-03
目标设备：安卓手机（任意 7.0+，内存 4 GB 以上）
技术路线：Termux + llama.cpp，纯本地 CPU 推理

## 一、结论

手机上可以部署大模型，1.5B 这个规模属于轻量级，4 GB 内存的手机就能跑，6 GB 以上体感舒适。
当前方案的硬门槛不是算力而是内存，所以**必须用量化模型**，不能直接跑 FP16 原始权重。

选定的组合是 Qwen2.5-1.5B-Instruct + Q4_K_M 量化 + llama.cpp，特点是完全离线、
不需要 Root、不依赖任何云服务，还能顺带对外提供一个 OpenAI 兼容接口。

## 二、模型选型

| 模型 | 量化后体积 | 运行内存 | 说明 |
|---|---|---|---|

| Qwen3-0.6B Q4_K_M | 0.38 GB | 约 0.8 GB | 本地已有，速度更快，能力弱一档 |

Q3 以下省内存但质量明显下滑，不建议。

### 最终采用的技术路线：预编译二进制，零编译

**关键决策：放弃在手机上编译，改用官方 Android arm64 预编译包。**

在手机上编译会在链接阶段硬失败：

```
ld.lld: error: undefined reference: std::__ndk1::__hash_memory(void const*, unsigned long)
>>> referenced by ../../bin/libllama-server-impl.so (disallowed by --no-allow-shlib-undefined)
```

`std::__ndk1` 是 Android libc++ 的命名空间，该符号在这一版 `libc++_shared.so` 里未导出 ——
属于 Termux 预置 clang 21 与 llama.cpp 新版源码的 **libc++ ABI 不匹配**，重试无用。
当时源码共 779 个文件，只编到 82 个 `.o` 就卡在链接。

改用官方 CI 用 Android NDK 产出的 bionic 版本：

| 项目 | 值 |
|---|---|
| 资产 | `llama-b11146-bin-android-arm64.tar.gz` |
| 大小 / 校验 | 72,535,052 字节，SHA256 `b0d154df...a79687`（实测一致） |
| 下载耗时 | 9 秒（峰值 9.55 MB/s，手机直连 GitHub） |
| 落地位置 | `~/llama-android/llama-b11146/`（267 MB） |

同一 release 里的 `ubuntu-arm64` 是 glibc 版（树莓派用的就是它），**不能混用**：
两者指令集相同但 C 运行库不同，glibc 版在 Android 上会
`interpreter /lib/ld-linux-aarch64.so.1 not found`。

### 三个必须记住的坑

**1. bionic linker 不支持 `$ORIGIN` RPATH。**
直接运行解压出来的二进制会失败：
`CANNOT LINK EXECUTABLE "./llama-cli": library "libllama-cli-impl.so" not found`。
必须设 `LD_LIBRARY_PATH` 指向二进制所在目录。已用 `~/.local/bin/llama-dispatcher`
分发器（按 `$0` 名字转发）自动处理，并为 22 个命令建了软链接。

**2. `llama-server` 没有界面是正常的。**
它启动后不显示对话界面，看起来像卡住，实际在监听 HTTP 端口。
而 `llama-cli` 是带边框的交互界面。两者行为完全不同，别混淆。

**3. `-st` 必须加，旧参数 `-no-cnv` 已删除。**
不加 `-st` 时 `llama-cli` 进入交互模式等待输入，在脚本/管道里调用会被误判为卡死；
用 `-no-cnv` 会报 `invalid argument: -no-cnv`。

**4. Termux 里不要用 heredoc 建脚本。**
dash 的 heredoc 需要往 `/data/local/` 写临时文件，app UID 无权写，会静默产出
**0 字节文件**（`chmod` 却仍执行，所以看起来像成功了）。建脚本请用本机生成后 `cp`。
同理，`ln` 要用 Termux 的 `/data/data/com.termux/files/usr/bin/ln`，
`/system/bin/ln` 在 app 私有目录会报 `Read-only file system`。

### 实测性能（分冷态与持续两种）

用 `llama-bench` 与真机 HTTP 请求分别实测，**两者差距接近一半，原因是热降频**：

| 场景 | 状态 | 生成速度 | 提示处理 |
|---|---|---|---|
| `llama-bench` tg | 冷态（SoC 30°C） | **22.62 t/s** | 54.32 t/s |
| 真机 HTTP（bench-server.ps1） | 冷态首轮 | 15.35 t/s | 54.10 t/s |
| 真机 HTTP 三次平均 | 已升温 | 13.36 t/s | — |
| `llama-bench` tg | 持续压测（SoC 77°C） | **9.89 ~ 12.81 t/s** | 16.30 ~ 20.43 t/s |

### 热降频是这台机器的真实瓶颈

实测证据链（同一天、同一命令，仅温度不同）：

```text
冷态启动           SoC 30°C   cpu7 上限 2300MHz(未限)   →  22.62 t/s
连续压测后         SoC 76°C   cpu7 上限 1959MHz          →   9.89 t/s
继续压测           SoC 77°C   三轮递减 11.63→11.41→10.42
热保护触发         SoC 58°C   cpu7 上限 335MHz(最低档)   →   5.56 t/s
```

`cpu7` 硬件上限 2.30GHz，被热限流依次压到 2.05GHz → 1.96GHz → **335MHz**。
三个集群的上限同时被压低：cpu0 1550→1400MHz、cpu4 2180→2050MHz、cpu7 2300→2050MHz。

**这个结论影响使用方式**：短问答（十几秒）能吃到 20+ t/s，连续对话十几分钟后会掉到
10 t/s 上下并继续下滑。要恢复满速得让机器静置降温，不是软件能解决的。

顺带排除的两个猜测：
- **不是供电问题**：实测 `USB powered: true`、电量 89%。
- **不是线程数没设对**：热态下复测 `-t 6/7/8` 得到 6.79 / 7.96 / 5.56，与冷态的
  「8 最优」结论相反 —— 这正说明该轮数据被降频污染，不能作为线程配置依据。
  线程结论以冷态为准（`-t 8` 最优）。

### Qwen3 的思考模式必须关闭

Qwen3 默认开启思考模式，会把 `max_tokens` 全花在思考上、`content` 返回空字符串，
`finish_reason` 为 `length`，表现为「模型不回答」。

逐个实测了四种服务端关法（Qwen3-0.6B，问 "What is 2+2?"，`max_tokens=60`）：

| 启动参数 | 返回 content | finish_reason | 判定 |
|---|---|---|---|
| 不加参数 | `""`（空） | length | 无效 |
| `--reasoning-budget 0` | `"Okay, the user is..."` | length | **无效** |
| `--reasoning off` | `"2"` | stop | **有效** |
| `--chat-template-kwargs '{"enable_thinking":false}'` | `"2"` | stop | 有效 |

`--reasoning-budget 0` 看起来最像正确答案，实测却无效。已采用 `--reasoning off`
写进 `start-server.sh`（默认关闭，`THINK=1` 可开）。

### 附带结论：adb 其实可以驱动 Termux（更正早前判断）

早前认为「非 root 手机无法用 adb 触发 Termux 命令」，那是针对
`com.termux.RUN_COMMAND` 广播而言的，该结论本身成立：

| 尝试 | 结果 |
|---|---|
| `am broadcast ... com.termux.RUN_COMMAND` | 广播被投递，但脚本未执行 |
| 重启 Termux 使 `allow-external-apps=true` 生效后重试 | 仍不执行 |
| `pm grant com.termux com.termux.permission.RUN_COMMAND` | 失败：`Package com.termux has not requested permission` |

根因：`RunCommandService` 声明了 `com.termux.permission.RUN_COMMAND`
（protectionLevel `dangerous`），要求调用方持有；而该权限在 Termux 自身清单中未声明，
所以 adb shell 既无法持有也无法代授。

**但真正管用的通道是 `adb shell run-as com.termux`** —— 它以 Termux 用户身份
（UID 10279）在 app 私有目录中执行，工具链、环境变量、私有存储全部可见，
配合 `setsid` 还能脱离 adb 会话后台运行。本次编译、下载、推理、服务启动
全部由此完成，**全程无需在手机上手工粘贴任何命令**。
唯一限制是 `/proc/loadavg`、`/proc/<pid>/io` 等部分 procfs 节点对 app 域不可读。
