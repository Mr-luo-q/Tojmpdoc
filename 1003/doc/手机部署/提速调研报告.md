# 提速调研报告：手机端 llama.cpp 推理

调研日期：2026-10-03
设备：华为 Pura 70 Pro+（HBN-AL80），Kirin 9010
模型：Qwen2.5-1.5B-Instruct Q4_K_M
现状：瞬时 22.6 t/s，热降频后掉到 5.6~13 t/s

## 一、先明确瓶颈在哪

生成阶段（decode）是**内存带宽受限**的：每生成一个 token 都要把全部权重从内存读一遍。
提示处理阶段（prefill）是**计算受限**的：一次矩阵乘处理整段提示词。

实测反推的有效带宽：

```text
1.117 GB（模型体积） ÷ (1 / 22.62 t/s) ≈ 25.3 GB/s
LPDDR5X 4266MHz × 4×16bit 理论值      ≈ 68.2 GB/s
占比 ≈ 37%
```

37% 对手机 SoC 属于正常水平。而 CPU 大核实测只跑在 1.12~1.62GHz（上限 2.30GHz），
说明**不是算力墙，是访存墙**。这个判断决定了下文的取舍。

## 二、调研结论：NPU 和 GPU 对 decode 都没有优势

这是本次调研最重要的发现，来自清华与北京交大的跨层测量研究
[Is Your NPU Ready for LLMs?](https://ar5iv.labs.arxiv.org/html/2607.05475)（覆盖
llama.cpp / MNN / MLC-LLM / MLLM / GENIE 五个框架，CPU / GPU / NPU 三种后端，
400+ 组配置）。它提出「相位拆分」（phase split）：

```text
                    prefill（计算受限）        decode（内存受限）
──────────────────────────────────────────────────────────────────
NPU                 强，峰值 >1400 t/s        弱，落后于 CPU
                    擅长大批量固定形状          讨厌小核动态形状
GPU                 llama.cpp Vulkan 能追上    接近 CPU
CPU                 弱                       最快的一档（约 70 t/s）
```

原因很具体：**NPU 是静态图执行，需要预先分配固定形状的大窗口**。而 decode 是
「一次一个 token、上下文持续增长」的小核动态负载，与 NPU 的架构偏好正面冲突。
论文实测上下文从 16 增到 4096 token 时，NPU 留下 20.0~23.8% 的 decode 吞吐余量没用上。

这条结论对本机意味着：**即使绕过华为 CANN 的接入障碍，NPU 也不会让 decode 更快。**

该论文还给了同一模型（Qwen2.5-1.5B w4）的横向数据，可作为参照系：

| 后端 | 框架 | 设备 | prefill t/s | decode t/s |
|---|---|---|---|---|
| CPU | llama.cpp | 小米 17 | 417.3 | 51.6 |
| CPU | llama.cpp | 一加 15 | 299.9 | 55.7 |
| CPU | llama.cpp | 小米 15 | 329.2 | 53.9 |
| CPU | llama.cpp | 小米 14 | 157.2 | 34.5 |
| CPU | **MNN** | 小米 17 | 349.5 | **19.0** |
| GPU | llama.cpp | 小米 17 | 569.7 | 38.8 |

两点值得注意。其一，同为骁龙旗舰，本机 decode 只有 22 t/s，是小米 14（骁龙 8 Gen 3）
的 64%、小米 17 的 43% —— 差距来自 Kirin 9010 相对落后的内存子系统，属于硬件差异。
其二，**MNN 的 decode 反而比 llama.cpp 慢得多**（19.0 vs 51.6），
所以「换个国产框架试试」这条路在 CPU 上没有收益。

## 三、GPU 与 NPU 在本机的现实可行性

| 路子 | 障碍 | 判断 |
|---|---|---|
| NPU（达芬奇） | 只能走华为 CANN / CANN Kit，非 Android 通用 API，Termux 内不可达；且如上所述对 decode 无优势 | **放弃** |
| GPU（Maleoon 910） | 官方不发布 Android arm64 Vulkan 构建；上游对 Mali 系 GPU 的 Vulkan 后端仍在修崩溃（[Maleoon 设备特性导致进程被杀](https://github.com/ggml-org/llama.cpp/issues/28812)） | **放弃** |
| GPU（高通专用路径） | 官方 `android-arm64-snapdragon` 包针对 Adreno + Hexagon，与 Maleoon 无关 | **不适用** |
| 自己做交叉编译 | 需 Android NDK；本机无网络（curl 到 GitHub 零字节）；且 Vulkan 收益主要在 prefill，对本机主诉求（decode）帮助有限 | **性价比低** |

顺带一个旁证：llama.cpp 自己也有
[Adreno GPU 时钟节流问题](https://github.com/ggml-org/llama.cpp/issues/27191)——
「KGSL 功耗约束导致提交之间被限频，拖累 tg128」。说明移动端 GPU 后端普遍受功耗管理困扰，
不是换后端就能简单变快。

## 四、真正有效的方向：调度与热管理

同一篇论文的第三点发现指向这里：**调度不当造成最多 40% 的能量浪费**，
其中「线程与核心亲和性配置不当」单项就能造成 **35% 的性能波动**。
论文给出的优化手段（细粒度 DVFS 调优）在某些后端能回收约 50% 的浪费能量。

本机实测印证了热降频的严重程度：

```text
冷态              SoC 30°C   cpu7 上限 2300MHz   22.62 t/s
连续压测          SoC 76°C   cpu7 上限 1959MHz    9.89 t/s
热保护触发        SoC 58°C   cpu7 上限 335MHz     5.56 t/s
```

温度上升速度极快：一次 15 秒的基准测试就能让 SoC 从 46°C 冲到 73°C。

另有一篇预印本提出
[自适应热调度架构](https://zenodo.org/records/18317171)，在 token 生成批次之间插入
「不可察觉的微暂停」让热量快速散出，实测把峰值温度降低 12%、连续推理时长延长 40%。
思路值得借鉴，但 llama.cpp 没有原生命令实现它。

### 本机的每瓦性能实测

方法：每组都冷却回 41°C 基准起跑，用「tps ÷ 温升」近似每瓦性能。

| 配置 | tps | 温升 | 每瓦性能 |
|---|---|---|---|
| 全部核 `-t 8` | 22.52 | 27°C | 0.834 |
| 大中核 `-t 4` | 20.11 | 16°C | 1.257 |
| 全部核 `-t 8`（重测） | 22.39 | 13°C | **1.722** |
| 大中核 `-t 3` | 21.25 | 15°C | 1.417 |
| 全部核 `-t 6` | 21.97 | 25°C | 0.879 |
| 全部核 `-t 4` | 20.04 | 22°C | 0.911 |
| 大中核 `-t 2` | 14.53 | 19°C | 0.765 |
| 仅小核 `-t 4` | 2.13 | 0°C | 不适用 |

**必须说明测量质量问题**：同一个 `-t 8` 配置两次测得温升 27°C 与 13°C，波动一倍以上。
原因是手机上微信等后台应用持续占用 CPU（实测 SoC 温度在无负载时也在 41~56°C 之间浮动）。
所以上表的**绝对值不可作为精确结论**，只能读出方向性判断。

方向性判断有三条：

```text
1. -t 8 仍是最快配置（22.4~22.5 t/s，多次复现），且持续压测下最稳
   （四窗口 26.38 → 21.09 → 21.67 → 22.94，没有崩塌）

2. 限制核心范围不能省热。仅大中核 -t 4 反而出现衰减（26.07 → 18.46 → 19.95 → 15.82），
   因为可用核心变少、单核压力变大

3. 小核（Cortex-A510 1.55GHz）跑 1.5B 几乎无用：2.13 t/s，但温升为零
   —— 它省电却太慢，不适合单独承担
```

## 五、按性价比排序的行动清单

```text
优先级 1  换更小的模型 —— 唯一能带来数量级收益的手段
          Qwen3-0.6B Q4_K_M 体积 0.38 GB，是 1.5B 的 34%
          按访存公式外推应达 60+ t/s，且发热大幅下降
          代价：中文能力弱一档。日常问答/摘要够用，复杂推理不行

优先级 2  接受热的现实，按用途选线程数
          追求瞬时最快、短问答：-t 8
          长时连续对话、在意电量：大中核 -t 3（21.25 t/s，温升较低）

优先级 3  物理散热 —— 对持续负载最有效
          半导体制冷背夹已有第三方实测支持（如对《Mobile Legends》的
          Peltier 制冷对照实验），能显著降低表面温度、延后降频
          这是唯一能同时改善「速度」与「稳定性」的外部手段

优先级 4  调小上下文 -c —— 减小 KV 缓存占用，间接减轻带宽压力
          但收益有限：1.5B 的 KV 缓存每 token 仅约 28 KiB（GQA 6:1 很省）

优先级 5  换更大内存带宽的设备 —— 根治方案，非本机可改
```

明确**不做**的事：走 NPU、自己编 Vulkan、换 MNN、在热机状态下反复调参。
前三个已由调研与实测排除，第四个只会产生不可复现的数据。

## 六、已实测验证：换 0.6B 模型的实际收益

第五节的优先级 1 已实测确认。方法与前面一致：每组都冷却回 41°C 基准起跑，
两轮顺序对调以排除顺序效应。

| 模型 | prefill t/s | decode t/s | 温升 | 每瓦性能 |
|---|---|---|---|---|
| 1.5B Q4_K_M（第 1 轮） | 49.4 | 18.35 | +36°C | 0.510 |
| 1.5B Q4_K_M（第 2 轮） | 50.2 | 22.28 | +36°C | 0.619 |
| 0.6B Q4_K_M（第 1 轮） | 132.3 | **49.65** | +20°C | 2.482 |
| 0.6B Q4_K_M（第 2 轮） | 133.7 | **49.42** | +18°C | **2.746** |

结论：

```text
decode 速度          18.35~22.28  →  49.42~49.65 t/s     提升约 2.4 倍
prefill 速度         49.4~50.2    →  132.3~133.7 t/s     提升约 2.7 倍
温升                  +36°C        →  +18~20°C            降低约 44%
每瓦性能             0.510~0.619  →  2.482~2.746          提升约 4.0 倍
```

0.6B 的持续压测（四个 128-token 窗口）也没有出现 1.5B 那种崩塌：

```text
1.5B 持续    26.38 → 21.09 → 21.67 → 22.94   （约 22 附近，但曾实测掉到 5.56）
0.6B 持续    36.15 → 48.12 → 36.50 → 47.25   （36~48 之间波动，未崩塌）
```

窗口间 36 与 48 的交替波动，推测是 llama-bench 每次重启进程、模型重新加载导致的
（0.6B 加载快，但仍需重新分配 KV 缓存），不是降频。

一个值得注意的细节：0.6B 反推的有效带宽是
`0.397 GB ÷ (1 / 49.5 t/s) ≈ 19.7 GB/s`，**比 1.5B 的 25.3 GB/s 更低**。
这说明小模型没能把带宽压榨得更充分（固定开销占比上升），
但因为权重体积只有 34%，净速度仍大幅领先。**这是访存公式的典型表现：
速度取决于「体积 ÷ 带宽」，而小模型在体积上赢的幅度远大于带宽效率上的损失。**

## 七、走 llama-server 的真实请求对比

纯 `llama-bench` 的数字是理想负载。真实使用走 HTTP，所以另测一组。
**每次请求都先读 `/v1/models` 校验服务实际加载的模型**，避免测错对象
（第一版测试脚本就犯了这个错：切换模型后没校验，把 1.5B 的数据当成了 0.6B 的）。

| 模型 | 思考模式 | prefill t/s | decode t/s | content |
|---|---|---|---|---|
| 1.5B | 不适用 | 39.9 | 17.22 | 正常完整 |
| 1.5B | 不适用 | 11.5 | 17.35 | 正常完整 |
| 0.6B | **默认开启** | 80.4 | 33.96 | **空** |
| 0.6B | **默认开启** | 28.6 | 49.78 | **空** |
| 0.6B | **关闭** | 51.8 | **51.78** | 正常完整 |

服务端 1.5B decode 稳定在 17.2~17.3 t/s，与 `llama-bench` 的 18~22 基本吻合，
差异来自 HTTP 层与批处理开销。**0.6B 关闭思考模式后 51.78 t/s，是 1.5B 的 3.0 倍。**

### 必须处理的坑：Qwen3 默认思考模式

上表 0.6B 那两行 `content` 为空不是 bug，是 Qwen3 的默认行为。它会把
`max_tokens` 全部消耗在思考上，`finish_reason` 返回 `length`，答案一个字都不输出：

```json
{"finish_reason":"length",
 "content":"",
 "reasoning_content":"Okay, the user wants to know what model quantization is.
                      Let me start by recalling what model quantization is..."}
```

思考内容走独立的 `reasoning_content` 字段，`content` 保持空。`max_tokens=64` 时
连思考都写不完，所以看起来像「模型没反应」。

两种关闭方式**都必须在服务端启动时指定**，不必每次提问都加 `/no_think`。
逐个实测了四种关法（Qwen3-0.6B，问 "What is 2+2?"，`max_tokens=60`）：

| 启动参数 | 返回的 content | finish_reason | 判定 |
|---|---|---|---|
| 不加参数 | `""`（空） | length | 无效 |
| `--reasoning-budget 0` | `"Okay, the user is..."` | length | **无效** |
| `--reasoning off` | `"2"` | stop | **有效** |
| `--chat-template-kwargs '{"enable_thinking":false}'` | `"2"` | stop | 有效 |

`--reasoning-budget 0` 看起来最像正确答案（「思考预算为 0」），实测却无效 ——
思考文本只是从 `reasoning_content` 挪回了 `content`，仍然吃光 token。
采用最简洁的 `--reasoning off`，已写进 `start-server.sh` 并验证：关闭后
直接提问可得 `"2 + 2 = 4"`（decode 47.0 t/s）与完整切题的一句式解释（37.2 t/s）。

## 八、切换模型

`start-server.sh` 已支持模型切换：

```bash
bash ~/start-server.sh            # 默认 1.5B（质量优先）
MODEL=06 bash ~/start-server.sh   # 0.6B（速度优先，快约 3 倍）
```

用 0.6B 时**务必关闭思考模式**，否则回答会被思考过程吃光。浏览器界面下可在
提问末尾加 `/no_think`；程序调用时传 `chat_template_kwargs`。

## 九、待验证项

**0.6B 的对话质量是否够用。** 速度已确认有 2.4~3.0 倍提升，但 Qwen3-0.6B 的中文能力
比 Qwen2.5-1.5B 弱一档，且默认带思考模式。需要在实际问答场景试用后判断取舍。

**中文提示词在本报告的测试方法下会失效。** 通过 `adb shell` 把中文传给 curl 时会被
shell 编码破坏（模型收到乱码，回「I can't see any text」），所以本报告的问答对比
全部用英文提示词。这只影响我的测试手段，**不影响手机端实际使用** ——
在 Termux 里直接输入中文、或在浏览器界面输入中文都正常（早先用 `llama-cli`
实测中文问答「我是阿里云开发的大规模语言模型，我叫Qwen。」正常）。
