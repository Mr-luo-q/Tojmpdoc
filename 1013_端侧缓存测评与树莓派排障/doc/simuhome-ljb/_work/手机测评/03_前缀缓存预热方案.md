# 03 前缀缓存预热：把 system 段提前灌进 KV

> 核对时间：2026-10-13
> 依据：`02_端侧实测结果.md` 的实测数据、`tools/traj_replay.py` 的 --warmup 实现，
> 以及本次扫描时观察到的跨样本缓存命中
> 状态：方案与证据已定；专门的 A/B 实测**尚未跑**（手机未连线），待补。

## 1 boss 的要求，以及一处必须改的地方

要求原话的意思是：**把首轮提示词里固定的那部分提前存进前缀缓存，之后处理时就省掉这部分的 prefill**。
这个大方向成立，而且收益最大的一块就在这里。但"头两轮都可以存进前缀缓存"要改成一句话：

```text
cache 只能跨样本存 system 段；observe_home 那段跨不了样本
```

原因是顺序，不是内容。一条轨迹的真实顺序是：

```text
system(固定) → user_request(每条都不一样) → 第1次工具调用 → observation → ...
```

前缀缓存要求**逐 token 完全一致**，从第一个不同的 token 起，后面全部作废。observe_home 的观察排在
用户那句话**之后**，用户那句每条样本都不同，前缀在这里就分叉了，所以那段没法跨样本预存。
它在同一条轨迹内部当然会被复用——但那是普通的前缀缓存，不是"预存"。

能跨样本共享的只有 system 段，而它恰好是首轮的大头：实测 **1069 token**，
首轮总共 1088 token，**占 98%**，用户那句只占 19 token。

## 2 可缓存 / 不可缓存的分界

```text
                       能不能跨样本预存   实测大小      说明
system 段（A_policy+工具表）   能            1069 token    和样本无关，五个样本的命中都是 1069
user_request                 不能          约 19~35 token 每条不同，前缀在这里分叉
observe_home 及其返回          不能（跨样本）  约 314 字符   排在用户那句之后
                              能（同一轨迹内）             普通前缀缓存已覆盖
第 2 轮之后的一切               同一轨迹内复用  ——            同上
```

## 3 落地方案

```text
模块      预热

职责      服务启动后，把 system 段一次性灌进 KV 槽，让之后每条轨迹的首轮
          只剩 user_request 那十几个 token 要算

输入      样本的 system 消息（A_policy 填入公开工具表），对所有样本是同一份

输出      无（副作用是 KV 槽里多了一段 1069 token 的前缀）

读取      与正式请求完全相同的那段 system 文本，必须逐字符一致

写入      只写模型侧的 KV，不落盘

不负责    不改变任何一条轨迹的内容、长度、轮数；不预热 user_request 及之后的内容

对应文件  tools/traj_replay.py 的 --warmup system
```

用法就是加一个参数，先打一条只含 system 的请求：

```powershell
D:\Anaconda\python.exe _work\手机测评\tools\traj_replay.py `
    --host http://127.0.0.1:18080 --sample sc_T1_001 --mode traj --warmup system
```

`--warmup` 三档的区别：`none` 不预热；`short` 打一个 1 token 的短请求，只为 CPU 升频
（以前一直用的是这档，它对缓存没用）；`system` 才是真正的预热。

## 4 已有证据与预期收益

已经**实测**到的旁证：T1~T5 扫描时，样本 2~5 的首轮命中都是 1069 token、新增只有 13~39 token，
TTFT 落到 0.82~1.93 s；而同一条轨迹在真正冷启动时首轮要 38.5 s。

```text
                        冷启动（现状）      system 预热后
首轮要算的 token         1088               约 19（只剩用户那句）
首轮 TTFT                38.5 s             1~2 s（旁证区间）
整条 5 轮轨迹墙钟        68.1 s             约 30 s（推算）
关缓存对照              308.5 s             —— 预热对它无效，它每次都全算
```

**收益只落在"服务启动后的第一条轨迹"上。** 服务跑热之后，system 段本来就一直待在 KV 里，
后面每条轨迹的首轮已经在命中它了——这正是 T1~T5 扫描里样本 2~5 首轮 TTFT 只有 0.82~1.93 s 的原因，
那批 39.5 s/条的平均值本身就是"已预热"口径。所以：

```text
单次/交互式使用（服务刚起来，只跑一条）   68 s → 约 31 s，提升 2.1 倍
批量跑批（服务常驻，连跑 1000 条）        省下第一条的 37 s，摊到 1000 条上可忽略
真正的省时来自前缀缓存本身                308 s → 68 s（未预热）/ 31 s（已预热）
```

换句话说，预热解决的是"冷启动那一条特别吃亏"，不是给每条轨迹都提速。

## 4.1 这条收益到底值多少（先把话说透）

预热还有一层容易被忽略：**它本身也要花 38 秒**（把 system 段算一遍才能进 KV）。
所以它做的不是"省掉"，而是"把这段从用户等的第一条请求，挪到服务启动时"。

```text
自动前缀复用    已经一直在工作，不需要我们做任何事；每条轨迹的首轮都受益
显式预热        把 38 秒从"第一条请求"挪到"服务启动"，总量没变
存盘再读回      真正让它消失：读一份 KV 文件比算 38 秒快，且跨进程有效
                （--slot-save-path，本版本是否支持待确认）
```

所以收益的算法是 `37 秒 × 冷启动次数`：

```text
服务常驻跑批          冷启动 1 次      可忽略，不值得为它做工程化
短会话 / 频繁重启      冷启动 ≈ 会话数   才有意义
多设备并行            冷启动 = 设备数×会话数  最值得做
```

结论：**预热本身不构成优化项**，它是个"看部署形态才决定值不值"的手段。
真正值得投入的是存盘持久化（如果支持）与 CPU 锁频那 1.5 倍。
