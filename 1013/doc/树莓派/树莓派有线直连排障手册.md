## 2. 根因分析（这次到底坏在哪）

### 2.1 一句话结论

**网络不通的根因不是网线、不是 SSH、不是 IP 配置，而是 NetworkManager 根本没运行、且一个连接配置都没有。**

### 2.2 证据链

| 观测 | 命令/来源 | 含义 |
| --- | --- | --- |
| `NetworkManager 服务=inactive / enabled=enabled` | 树莓派 `systemctl is-active NetworkManager` | 服务是启用的，**开机却没启动起来** |
| `已保存的连接配置: total 0` | `ls /etc/NetworkManager/system-connections/` | NM 里**零个** profile → 网卡拿不到任何地址 |
| `eth0 DOWN` / `wlan0 DOWN` | `ip -br link` | 两块网卡都趴着 |
| `Could not find module named cc_netplan_nm_patch` | `/var/log/cloud-init-output.log` | **真正的元凶**：树莓派官方用于把 cloud-init 的 netplan 配置桥接到 NetworkManager 的补丁模块缺失 |
| 22 端口回 `Not allowed at this time` | 裸 socket 抓 banner | sshd 侧拒绝的表象（见 §5.3） |

### 2.3 因果链（完整解释）

```
烧卡时用 cloud-init 写了 network-config（wlan0 → smp、eth0 → dhcp）
        │
        ▼
镜像里缺少 cc_netplan_nm_patch 模块
        │  （cloud-init 日志只有 WARNING，不报错、不中断）
        ▼
netplan 配置从未被转换成 NetworkManager profile
        │
        ▼
/etc/NetworkManager/system-connections/ 为空
        │
        ▼
NetworkManager 起来也没东西可配 → 网卡全部 DOWN
        │
        ▼
树莓派既不在有线网、也不在热点 → 「怎么都连不上」
```

**关键教训**：cloud-init 的 WARNING 不能忽略。这句 `cc_netplan_nm_patch` 就是全案的钥匙，但它只出现在日志里，不影响启动、不弹错误。

### 2.4 为什么前几版修复会失败（同样重要）

我在 cloud-init 的 `bootcmd` 阶段（**开机第 9 秒**）调用了 `systemctl`：

```
bootcmd 执行 → systemctl enable ssh → 卡住（systemd 拒绝在 boot 早期变更状态）
     │
     ▼
cloud-init 的 bootcmd 是同步执行的 → 整个 boot 被拖住
     │
     ▼
启动没走完 → NetworkManager 永远不会被启动 → rc.local 也没机会在启动末期执行
     │
     ▼
日志停在 systemctl enable ssh 中途，救不回来
```

**关键教训**：**开机早期（`bootcmd`）绝对不要调 `systemctl`**。要调用就放到启动末期（`/etc/rc.local`）。

## 3. 排障时间线（方法论参考）

| 阶段 | 做法 | 结果 |
| --- | --- | --- |
| ① 配置对齐 | 查配置文档、`ipconfig`、`netsh` | 电脑有线口已有 `192.168.137.1/24`，链路显示 connected |
| ② 加副地址 | 给网口挂 `169.254.0.1/16`、`192.168.0.1/16` | 覆盖树莓派可能拿到的任何网段 |
| ③ 扫描 | 扫 `169.254.0.0/16` 全段（64 并行） | **无任何回应** |
| ④ 判定链路 | ping 时看网卡发包计数 | **发包数 0** → 包根本没进网卡 |
| ⑤ 抓包定位 | 自写迷你 DHCP 服务器监听 UDP 67 | **抓到 `DHCP DISCOVER MAC=dc:a6:32:f1:4e:c7 主机名=raspberrypi`** → 链路其实是通的！ |
| ⑥ 发现真问题 | 该服务器发 OFFER 报 `WinError 10049` | 源地址 `0.0.0.0` 无效 → 改为绑定具体地址 |
| ⑦ 拿到地址 | 迷你 DHCP 服务器发 `192.168.137.50` | 树莓派上线，但 SSH 回 `Not allowed at this time` |
| ⑧ 深挖 | 端口探测 | 8080=llama.cpp、8123=HomeAssistant 都正常，**只有 22 被拒** |
| ⑨ 读卡取证 | 拔卡 → 只读解析 ext4 rootfs | 排除 sshd 配置、`/etc/nologin`、fail2ban |
| ⑩ 全盘搜索 | 扫 rootfs 19814 个文件找那句拒绝语 | **0 命中** → 不是静态文本 |
| ⑪ 盲修通道 | 通过 bootfs 的 `user-data` 注入 `bootcmd` | 建立"断电状态下给树莓派下指令"的通道 |
| ⑫ 踩坑 | v1/v2 修复都失败 | **在 bootcmd 里调 systemctl 卡住了 boot** |
| ⑬ 破局 | 改为 bootcmd 只装 `/etc/rc.local`，修复放到启动末期 | **成功** |
| ⑭ 收尾 | SSH 进去清理 bootfs 临时文件 | 系统恢复干净状态 |

**方法论要点**：
1. **不要相信状态字符串**（`netsh` 说 connected、`sshd` 说 enabled），要用**计数/抓包**这类硬证据；
2. **抓不到包的时候，自己造一个监听器**（迷你 DHCP 服务器）；它能同时回答"链路通不通"和"对端是谁"；
3. **拿不到 shell 时，想办法造一条带外通道**（bootfs + cloud-init），别硬猜；
4. **一次只改一个变量**，并且**先想清楚执行时机**（很多失败不是内容错，是时机错）。

## 4. 可复用操作手册

### 4.1 Windows 给网口配多地址（覆盖未知网段）

```powershell
# 加副地址（需管理员）
netsh interface ipv4 add address name="以太网" address=169.254.0.1 mask=255.255.0.0
netsh interface ipv4 add address name="以太网" address=192.168.0.1  mask=255.255.0.0

# 查看 / 撤销
netsh interface ipv4 show config name="以太网"
netsh interface ipv4 delete address name="以太网" address=169.254.0.1
```

**为什么要加**：直连时若对端没有 DHCP，Linux 会退回 `169.254.x.x`（IPv4 link-local），
而 `192.168.137.1/24` 盖不住它，必须再挂一个 `169.254.0.1/16`。

**踩坑**：`netsh interface ipv4 add address` 的 `name=` **只认连接名，不认网卡 GUID**；
连接名是中文时，在非 UTF-8 控制台里会变乱码 → 报「文件名、目录名或卷标语法不正确」。
**策略**：中文连接名的脚本，要么用 `-InterfaceIndex`，要么确保脚本带 UTF-8 BOM 且控制台代码页正确。

### 4.2 无显示器盲修：通过 bootfs 给树莓派下指令

**适用**：树莓派连不上网络、又接不了显示器，只能拔卡。

**原理**：cloud-init 每次开机都会重跑 `bootfs/user-data`。实测日志里 10/02、10/12 各完整跑过一次。
所以只要往 `user-data` 里加东西，下次开机就会执行。

**推荐的两段式结构**（关键：bootcmd 必须极短、绝不能卡）：

```yaml
# bootfs/user-data 追加
bootcmd:
  - [ bash, -c, "base64 -d /boot/firmware/install-repair.b64 > /boot/firmware/install-repair.sh; timeout 60 bash /boot/firmware/install-repair.sh" ]
```

`install-repair.sh` 只做一件事：把真正的修复脚本装成 `/etc/rc.local` 并启用 `rc-local.service`。

```bash
#!/usr/bin/env bash
# install-repair.sh —— 只在 bootcmd 阶段跑，绝不含 systemctl
LOG=/boot/firmware/pi-repair.log
{
  base64 -d /boot/firmware/pi-repair.b64 > /etc/rc.local && echo "decoded OK"
  chmod 755 /etc/rc.local
  for u in /lib/systemd/system/rc-local.service /usr/lib/systemd/system/rc-local.service; do
    [ -f "$u" ] && ln -sf "$u" /etc/systemd/system/multi-user.target.wants/rc-local.service && break
  done
} >> "$LOG" 2>&1
```

真正的修复写在 `/etc/rc.local`（启动末期执行，`systemctl` 合法），见 §4.5。

**要点**：
- 脚本用 **base64** 存成 `xxx.b64`，避免 YAML 引号/换行问题；
- bootcmd 命令行**必须是单行**（我在注入时用了拼装，多行会破坏 YAML）；
- 注入前先备份 `user-data`，脚本要能**自动回滚上一次注入**，保证可重复运行；
- 注入后用 Python 的 `yaml.safe_load` **校验一遍**再插卡。

### 4.3 只读读取 SD 卡的 ext4 分区（不装任何驱动）

**用途**：Windows 读不了 ext4，但需要离线取证（看日志、看 sshd 配置、看 NM profile）。

```python
# 关键点 1：物理盘要提权才能打开；分区卷 (\\.\E:) 非提权可开但会报"设备未就绪"
DRIVE = "\\\\.\\PhysicalDrive2"
PART_OFFSET = 545259520          # rootfs 分区起始（LBA 1064960，520 MiB）

# 关键点 2：裸盘读取必须 512 字节扇区对齐！读 64 字节会报 err 87
def pread(self, off, n, base=0):
    off += base
    SECTOR = 512
    start = (off // SECTOR) * SECTOR
    end   = ((off + n + SECTOR - 1) // SECTOR) * SECTOR
    SetFilePointerEx(h, start, None, 0)
    ReadFile(h, buf, end - start, byref(got), None)
    return buf.raw[:got.value][off-start : off-start+n]
```

**流程**：读 MBR（偏移 0，512 字节）→ 解析分区表拿起始 LBA → 在该分区 `+1024` 处读超级块 →
校验 magic `0x53EF` → 解析块/inode → 遍历目录树读文件。

**踩到并解决的坑**：
| 坑 | 现象 | 解法 |
| --- | --- | --- |
| 非扇区对齐读 | `ReadFile` 返回 err 87「参数错误」 | 所有读都按 512 字节对齐 |
| 漏加分区偏移 | 读到的是磁盘开头（MBR 引导代码） | 所有读都 `+ PART_OFFSET`，包括超级块那次 |
| `recvmsg` 不存在 | Windows Python 无 `IP_PKTINFO` | 改用"绑定具体地址 + `sendto`" |
| 卷路径不能读 | `\\.\E:` 报「设备未就绪」 | 改用 `\\.\PhysicalDrive2` + 提权 |

**同类工具**：[read-ext4.py](read-ext4.py) / [read-ext4-elevated.py](read-ext4-elevated.py)（只读）、
[search-rootfs.py](search-rootfs.py)（全盘文本搜索，扫 19814 文件约 86 秒）。

### 4.4 Windows 上用密码 SSH（别跟 pexpect 较劲）

**结论：用 paramiko，最省事。**

```bash
pip install paramiko
```

```python
import paramiko
cli = paramiko.SSHClient()
cli.set_missing_host_key_policy(paramiko.AutoAddPolicy())
cli.connect("192.168.137.2", username="pi", password="<口令已脱敏>",
            look_for_keys=False, allow_agent=False, timeout=10)
_, out, err = cli.exec_command("hostname; ip -br addr", timeout=15)
print(out.read().decode())
```

**为什么不用 pexpect**：
- Windows OpenSSH 的 `ssh.exe` **从控制台读密码**，`pexpect.popen_spawn` 用管道喂不进去；
- `pexpect.spawn`（真 PTY）**在 Windows 上根本不存在**（`AttributeError: module 'pexpect' has no attribute 'spawn'`）；
- `-o UserKnownHostsFile=/dev/null` Windows 上**不生效**（要写 `NUL`），导致 "Permanently added ... known hosts" 的
  警告混进输出，还容易被 expect 模式误匹配。

**sudo（需要密码时）**：
```python
_, o, e = cli.exec_command("sudo -S <命令>")
o.channel.send("password\n")     # -S 让它从 stdin 读密码
```

### 4.5 树莓派侧：开机自愈脚本（/etc/rc.local）

放在 `/etc/rc.local`，由 `rc-local.service` 在**启动末期**执行 —— 此时 `systemctl` / `nmcli` 完全合法。

核心内容（完整版见 [pi-repair.sh](bootfs-user-data-patch/pi-repair.sh)）：

```bash
# 1) 启动网络管理服务
systemctl start NetworkManager

# 2) 写持久连接配置（关键！这是真正的修复）
cat > /etc/NetworkManager/system-connections/eth0-static.nmconnection <<'EOF'
[connection]
id=eth0-static
type=ethernet
interface-name=eth0
autoconnect=true
autoconnect-priority=100
[ipv4]
method=manual
address1=192.168.137.2/24
may-fail=false
[ipv6]
method=ignore
EOF
chmod 600 /etc/NetworkManager/system-connections/eth0-static.nmconnection

# 3) 兜底：不依赖 NM 也把网卡拉起来
ip link set eth0 up
ip addr show eth0 | grep -q '192.168.137.2' || ip addr add 192.168.137.2/24 dev eth0

# 4) SSH：软链接 + 启动，双保险
ln -sf /usr/lib/systemd/system/ssh.service /etc/systemd/system/multi-user.target.wants/ssh.service
rm -f /etc/nologin
mkdir -p /run/sshd && chmod 0755 /run/sshd
ssh-keygen -A >/dev/null 2>&1
systemctl enable --now ssh
ss -lnt | grep -q ':22' || setsid /usr/sbin/sshd >/var/log/pi-sshd.log 2>&1 < /dev/null &
```

**设计原则**：
- **幂等**：每次开机都跑，重复执行无副作用；
- **带兜底**：NM 不работ时用 `ip` 直接配，`systemctl` 不работ时用 `setsid sshd` 直接拉；
- **带日志**：全程写 `/boot/firmware/pi-repair.log`（FAT32，拔卡就能读），
  包含修复前后的 `ip -br link`、`nmcli device status`、`rfkill list`、`journalctl -u NetworkManager`；
- **不装哑巴**：失败时把 `systemctl status` / `journalctl` 的尾部也写进日志，方便下一次定位。

### 4.6 迷你 DHCP 服务器（判断链路 + 救急发地址）

**用途**：直连链路上没有 DHCP 服务器时，自己起一个。它同时是最好的**链路探针**：
只要抓到 `DHCP DISCOVER`，就证明"网线通、对端活着"。

**关键坑**：socket 绑 `0.0.0.0` 时 `sendto` 广播源地址是 `0.0.0.0` → `WinError 10049` 拒绝发送。

```python
# 正解：直接绑定到有线口的地址，源地址自然正确
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.setsockopt(socket.SOL_SOCKET, socket.SO_BROADCAST, 1)
s.bind(("192.168.137.1", 67))     # ← 关键：不是 0.0.0.0
...
s.sendto(reply, ("255.255.255.255", 68))
```

完整实现见 [dsh-dhcp-server.py](dsh-dhcp-server.py)（含 DHCP 报文解析/构造）。

**另一个坑**：防火墙默认 `BlockInbound`，入站 DHCP 会被吞。需要放行：
```powershell
netsh advfirewall firewall add rule name="DSH-Pi-DirectLink-DHCP" dir=in action=allow protocol=UDP localport=67,68 profile=any
```

### 4.7 修复脚本的"回滚"设计


## 5. 踩坑清单（按类别）

### 5.1 Windows 侧

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| `Get-NetAdapter` 被沙箱拒 | `HRESULT 0x80041003 拒绝访问`（WMI/CIM 层） | 改用 `ipconfig` / `netsh` / `Get-WmiObject Win32_NetworkAdapter` / `Get-Counter` |
| `netsh` 的 `Connected` 不可信 | 显示 connected，实际收不到包 | 用**发包/收包计数**判定；`Get-Counter "\Network Interface(...)\Packets Sent/sec"` |
| `netsh` 不认网卡 GUID | `name="{GUID}"` 报「语法不正确」 | 只认连接名；中文连接名要处理编码 |
| 中文连接名 + 非 UTF-8 控制台 | 报「文件名、目录名或卷标语法不正确」 | 脚本存 **UTF-8 带 BOM**；或改用索引定位 |
| 非提权进程网络视图不全 | 普通令牌下 `ipconfig` 只显示 2 个地址，提权后 4 个 | 改 IP / 改防火墙 / 注册计划任务都要提权 |
| 提权脚本"静默无输出" | `Start-Process -Verb RunAs` 起的窗口一闪而过 | 让脚本**把输出重定向到日志文件**，再读日志 |
| `.ps1` 含中文必须带 BOM | Windows PowerShell 5.1 按 GBK 解码 → 中文吃掉引号 → 语法错误 | 一律 `UTF8Encoding($true)` 保存；或写成纯 ASCII |
| PowerShell here-string 终止符 | `@'...'@` 内出现 `&&` 等被判成语句 | 改用**数组 + join** 拼装文本 |
| USB 读卡器磁盘被置"脱机" | 卷全部消失，`online disk`/`rescan` 报 VDS「找不到对象」 | 只能**物理拔插**读卡器重新枚举 |
| 机身 microSD 卡槽会蓝屏 | bugcheck `0x00000050`，点名 `bhtsddr.sys` | **只用 USB 读卡器**，别碰机身卡槽 |
| 裸盘读取必须扇区对齐 | 读 64 字节报 err 87 | 按 512 字节对齐读 |
| Windows ssh 密码自动化 | pexpect 各种失败 | **用 paramiko** |
| `UserKnownHostsFile=/dev/null` 无效 | "Permanently added ... known hosts" 混进输出 | 用 `NUL` |

### 5.2 树莓派侧

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| **缺 `cc_netplan_nm_patch`** | cloud-init 只报 WARNING；netplan 配置永不进 NetworkManager | 手工写 NM profile（`.nmconnection`）到 `/etc/NetworkManager/system-connections/` |
| **bootcmd 里调 systemctl** | boot 被卡住，启动走不完 | 修复脚本放 `/etc/rc.local`（启动末期） |
| `ssh.socket` 与 `ssh.service` 共存 | 套接字激活与独立守护进程互相干扰 | `systemctl mask ssh.socket`，只留 `ssh.service` |
| `ssh.service` 的 enabled 状态骗人 | `enabled=enabled`，但 `multi-user.target.wants/` 里没有软链接 → 开机不启动 | 手工建软链接，或 `systemctl enable ssh` |
| sshd 需要 `/run/sshd` | 该目录缺失时 sshd 起不来 | `mkdir -p /run/sshd && chmod 0755` |
| 直连没有 DHCP | 树莓派 eth0 只有 `dhcp4`，链路上没人发地址 → 一直沉默 | 电脑侧挂 `169.254.0.1/16` + 自己起 DHCP；或直接给 eth0 配静态 |
| 无线只在 5GHz 扫描 | `iw dev` 显示 `channel 34 (5170 MHz)`，热点在 2.4GHz 就找不到 | 热点开 2.4GHz / 打开「最大兼容性」 |
| 直接拔电源 | `s_state=0x0001`（EXT4_ERROR_FS），文件系统被标记错误 | 先 `sudo poweroff`；已损坏就 `sudo touch /forcefsck && sudo reboot` |

### 5.3 那句 `Not allowed at this time` 的解释

- 它是 SSH 连上来后**被树莓派主动掐断**时客户端看到的文本；
- 在 rootfs 里**全盘搜索 19814 个文件，0 命中** → 不是任何静态配置文件的内容；
- 最可能的来源：**`/etc/nologin` 文件**——sshd/PAM 在拒绝非 root 登录时，会把该文件内容
  **原样打印给客户端**然后关闭连接。修复脚本里的 `rm -f /etc/nologin` 正好能清掉它；
- 修复（NetworkManager + ssh 正常）之后**该报错彻底消失**，SSH banner 恢复为
  `SSH-2.0-OpenSSH_10.0p2 Debian-7+deb13u4`。

> 结论：这个报错是**症状**不是**病因**。遇到类似"端口开着但连不上"的情况，
> 先别去翻 sshd 配置，先确认 **NetworkManager 有没有跑、profile 有没有、`/etc/nologin` 在不在**。

## 8. 恢复与回滚

### 8.1 如果树莓派又连不上

1. 先确认**链路**：电脑网口能不能 ping 通 `192.168.137.2`？
   - 不通 → 看 `ip -br link`（拔卡读日志），重点看 eth0 是否 `NO-CARRIER`；
2. 确认 **NetworkManager**：
   - `systemctl is-active NetworkManager` → 必须是 `active`；
   - `ls /etc/NetworkManager/system-connections/` → 必须有 `eth0-static.nmconnection`；
3. 确认 **SSH**：`ss -lntp | grep :22`；
4. 以上任一缺失 → 检查 `/etc/rc.local` 是否还在、`rc-local.service` 是否 enabled。

### 8.2 如果 bootfs 的注入需要撤销

```powershell
# 恢复原始 user-data（去掉 bootcmd 注入）
sudo cp /boot/firmware/user-data.bak-<时间戳> /boot/firmware/user-data
# 删掉临时修复文件
sudo rm -f /boot/firmware/pi-repair.b64 /boot/firmware/install-repair.b64 \
           /boot/firmware/pi-repair.sh /boot/firmware/install-repair.sh /boot/firmware/pi-repair.log
```

### 8.3 兜底：重烧系统

如果卡或系统已不可靠，最省时间的做法是重烧。镜像与配置脚本仍保留在
[flash-sd.ps1](flash-sd.ps1) / [write-image.ps1](write-image.ps1) / [raw-write.py](raw-write.py) /
[cloud-init/](cloud-init/)，重烧后按 §4.2、§4.5 恢复有线直连，约 20 分钟。

## 9. 一句话总结

> **表层症状**（SSH 被拒、热点连不上、网线没反应）全都指向同一个**深层原因**：
> cloud-init 的 netplan 配置因为缺少 `cc_netplan_nm_patch` 而没有进入 NetworkManager，
> 导致 NetworkManager 零配置、网卡全 DOWN。
> 修复的关键不是写对配置，而是**把修复代码放对时机**（启动末期 `/etc/rc.local`，
> 而不是开机早期 `bootcmd`）——第一次失败纯粹是时机问题。
