## 1 要回答的问题

这是一次端侧时延与可行性评估，负载用合成数据的真实 token 画像，不去真装 HomeEnv 和工具服务。

```text
① 单轮        喂 ~1700 token 上下文、吐 ~100 token，量 TTFT 与总耗时
```

## 4 推算结果（1.5B，`-t 4`）

```text
口径                            单轮耗时      一条轨迹(5.62轮)    1000 条串行
无前缀缓存（每轮全量重算）        ~55~60 s      ~5.5~6.3 min       ~92~105 h
开前缀缓存（KV 复用）             ~10 s         ~1.6~1.8 min       ~27~30 h
开缓存 + system 段预存进 KV       ~10 s         ~1.1 min           ~18 h
```

拆开看这三行是怎么来的：

```text
无缓存    每轮把整段 prompt 重算一遍，总量 ≈ Σ prompt_t ≈ 6000~7000 token
          6800 ÷ 18.4 = 370 s，加 149 token 的生成 ≈ 17 s
缓存      每个 token 只算一次，总 prefill = 最终轮 prompt 1706 token
          1706 ÷ 18.4 = 93 s，加生成 ≈ 110 s
再预热    把 system 段（约 850 token）预先放进 KV 槽
          (1706 − 850) ÷ 18.4 = 47 s，加生成 ≈ 64 s
```

冷启动单独看最直观：**一次 1700 token 的提示词要 92 秒才吐第一个字**；缓存命中后只剩新增的
约 140 token，8~10 秒。0.6B 开缓存约 45 秒一条，无缓存约 2.4 分钟。

## 5 三步测试协议

用手机上的 `llama-server` 加 `adb forward`，配合已验证过的 `bench-server.ps1`。

```text
第1步  冷启动单轮
       用仓库真 system 提示词（A_policy + 工具表）补足上下文到 ~1700 token
       max_tokens=100，记 prefill_ms / TTFT / decode_ms

第2步  原样再打一次
       看 cache_n 命中多少、prefill_tok 掉到几、TTFT 掉到几秒

第3步  串一条 5~6 轮
       逐轮把「上一轮 prompt + 新观察」当前缀请求，累计到 ~6000 token
       开缓存与关缓存各跑一遍，量整条轨迹墙钟时间
```

## 6 前置条件与风险

```text
设备     USB 线（adb devices 里出现 7LPRYTBYU8NRY5SC）
         或手机开无线调试，给 IP:端口 + 配对码
网络     手机与电脑不通网，只能 adb forward；且 adb server 会被回收，
         建转发与跑脚本必须放进同一次命令调用
权重     手机上只有未微调的原模型（1.5B 原模型在固定 200 条上是 0/200）
         → 本轮只能得到「速度」，得不到「做对率」
版本     llama-server 的 --slot-save-path / cache_prompt 支持情况要现场确认
热       三连测时 decode 从 15.35 掉到 10.91，每次实测都要记电池温度
```
