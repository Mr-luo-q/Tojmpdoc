# 04 方案 A：预置固定头，不改协议

> 核对时间：2026-10-13
> 依据：`02_端侧实测结果.md` 的逐轮实测数据、`tools/traj_replay.py` 的 --skip-rounds
> 状态：脚本就绪、离线验收通过
> 前置条件：**不需要任何协议改动**——不动 A_policy、不动工具表、不动 D5 管线、不动数据集。
>           唯一前置是手机连线。随时可跑。

## 1 目标

把每条轨迹开头那一段先打一次，让它进 KV，然后把计时起点挪到 observe_home 给出回答之后，
得到"稳定态下单轮要多久"。

```text
现在      system → 用户话 → [模型]observe_home → [环境]房间清单 → [模型]inspect_room → …
方案 A    ↑ 这一段先预热一次，不计时          ↑ 计时从这里开始
```

任务定义、消息顺序、工具表全部不动，只改测量口径与预热时机。所以它不改变任何数据，
也不影响已有 1000 条轨迹的可比性。

## 2 技术前提

前缀缓存要求**逐 token 完全一致**：从第一个不同的 token 起，后面全部作废。
所以预热请求的 prompt 必须与要计时的第一步**逐字节相同**，否则命中会断在前面。

## 3 成本模型：预热不是免费的

```text
固定头 = system + 用户话 + observe_home 调用 + 房间清单
       实测约 1208 token（system 1069 + 用户话 19 + 调用 18 + 房间清单约 120）
       手机上按 26 t/s 算约 46 秒
```

这 46 秒不会消失，只是从不计时区间挪到了启动时。它值不值，取决于这块头能不能跨任务复用。

## 4 为什么它跨任务共享不了

固定头里带着"用户那句话"，而用户话每条任务都不同，前缀在它这里就分叉了：

```text
任务 1   system(1069) + 用户话A(19) + observe_home调用 + 房间清单 → …
任务 2   system(1069) + 用户话B(35) ✗ 从这里开始全部重算
                             ↑ 只有 system 那 1069 token 能共享
```

所以每条轨迹都得把这 1208 token 重算一遍，只是不算在计时区间里。

## 5 脚本规格

```text
模块      traj_replay.py 的 --skip-rounds

职责      把前 N 步的完整上下文先打一次当预热，再对第 N 步起的每一步计时并记录分段耗时

输入      --skip-rounds N   跳过并预热前 N 步；N=1 等于跳过 observe_home 那一步
          --host            手机 llama-server 地址（经 adb forward）
          --sample          样本 id，取 record.scenario_id
          --max-tokens      每轮生成上限，默认 32
          --dry-run         只打印要发的请求，不连手机
          --warmup          与 --skip-rounds 叠加；short 只为 CPU 升频

输出      终端：预热耗时一行 + 逐轮分段表 + 轮数 / prefill 合计 / 墙钟合计 /
                单轮平均墙钟 / 单轮平均 prefill
          logs\<样本>_<模式>_<cache|nocache>_<标签>_<时间戳>.json

读取      D:\项目\autodl-tmp\new_demo\runs\quota200_20261004_v2\data_processed\D_dataset.jsonl
          D:\项目\autodl-tmp\new_demo\data_static\D0_templates\A_policy.md

写入      只在 logs\ 下写实测记录；不改数据集、不改仓库源文件

不负责    不改消息顺序或工具表；不取消 observe_home；不评测正确率

对应文件  _work\手机测评\tools\traj_replay.py 与同名 traj_replay.md
```

用法：

```powershell
# 离线看要发什么
D:\Anaconda\python.exe _work\手机测评\tools\traj_replay.py --sample sc_T1_001 --skip-rounds 1 --dry-run

# 真机
D:\Anaconda\python.exe _work\手机测评\tools\traj_replay.py --host http://127.0.0.1:18080 --sample sc_T1_001 --skip-rounds 1
```

## 6 离线验收结果

```text
  第 1 步计时：4 条消息，3221 字符，末条角色 user   ← 与预热 prompt 逐字节相同，会接近全命中
  第 2 步计时：6 条消息，3823 字符，末条角色 user
```

第 1 步的 TTFT 会接近 0，那是"已经预热过"的效果，不是免费；预热耗时在输出里单列。

## 8 收益结论（已修正）

把预热成本算回去，两种口径的总耗时几乎一样：

```text
基线          67.5 s（5 步，含 observe_home 那一跳）
方案 A        42.9 s 预热 + 24.0 s 计时 = 66.9 s（4 步）
差值          0.6 s —— 就是省掉 observe_home 那一次生成的量级
```

原先估的 2 s 偏乐观：我把"用户那句话的 prefill"也算进收益里了，但那部分只是被挪到预热区间，
并没有消失。真正省掉的只有模型生成 observe_home 调用那一次（18 token，约 1 s）。

所以方案 A 的价值确实只在**测量口径**：单轮平均从 13.5 s 变成 6.0 s，
但那是因为最贵的那一轮（冷启动的 system 段）被排除在统计之外，不是真的变快了。

要让那 42.9 s 真正摊薄，只能靠方案 B 的按家共享。


`*` T1_001 的 0.1 s 是上一轮刚跑过同一条、前缀还在 KV 里的结果，不是正常值；
正常值是后四条那 3.8~6.8 s。

两个可用的结论：

```text
稳定态单轮   6.4~7.0 s（22 步平均 6.6 s），其中 prefill 约 4.7 s、decode 约 1.9 s
预热后第一步  五条样本的 TTFT 都是 137~149 ms —— 固定头命中的效果稳定复现
```

**预热成本从 42.9 s 掉到 3.8~6.8 s，本身就是个证据**：固定头 1208~1243 token 里，
只有 system 那 1069 token 被自动共享（服务热起来了），剩下的一百多个 token
（用户话 + observe_home 调用 + 房间清单）每条任务仍要各算一遍。
这正是第 4 节说的"固定头跨任务共享不了"，实机把它的代价量出来了。

## 9 结论

方案 A 是**测量口径**，不是优化：预热本身实测 42.9 s，与它替换掉的那一段（冷启动 38.4 s
加第二轮 4.3 s）等量，总耗时 67.5 s → 66.9 s，只省下 observe_home 那一次生成（约 0.6~1 s）。

它的用处有两个：一是把统计口径变成"稳定态单轮"，单轮平均 6.0 s，答案更贴近持续使用时的体感；
二是**给方案 B 探出了天花板**——预热命中后单轮 TTFT 只要 136 ms，说明按家共享一旦成立，
每条任务确实只剩用户那句话要算。要让那 42.9 s 真正摊薄，只能靠方案 B。
