# 02 端侧实测结果：一条真实轨迹在手机上跑

> 实测时间：2026-10-13
> 设备：Redmi K70E（`7LPRYTBYU8NRY5SC`，天玑 8300-Ultra，Android 14）
> 模型：Qwen2.5-1.5B-Instruct Q4_K_M（`~/models/qwen2.5-1.5b-instruct-q4_k_m.gguf`）
> 服务：llama.cpp 0.6.0 CPU-only，`llama-server -t 4 -c 4096 --metrics`，绑定手机 127.0.0.1:8080
> 通路：USB + `adb forward tcp:18080 tcp:8080`（本机 8001–8100 在 Windows 保留端口区间内，8080 绑不上）
> 样本：`quota200_20261004_v2` 里的真实轨迹
> 状态：开关缓存对照、单轮冷启动、T1~T5 各一条扫描全部跑完，数字自洽。

## 1 测法与口径

用 `tools/traj_replay.py` 按 `training/10-5_sft/data.py` 的 `reconstruct_messages` 口径重建消息：
system 是 A_policy 填入该样本的公开工具表，user 是 `scenario.user_request`，每轮 assistant 是工具调用
JSON、user 是 `"observation: " + last_tool_result`。逐轮把「截至上一轮」的消息前缀发给 llama-server，
上下文始终取自教师轨迹，模型生成的内容只用于计时。每次测量前先打一个 1 token 的短请求预热。

`sc_T1_001` 首轮 16.52 s 是这批里唯一的冷启动（换模型后 KV 清空），
其余样本首轮都在 1~2 s，仍是 system 段复用的结果。Qwen3-0.6B 需要 `--reasoning off`，
否则 max_tokens 会被思考内容吃光、content 留空。

两个模型的对照：

```text
               一条轨迹平均   单轮平均   prefill 速率   decode 速率
Qwen2.5-1.5B      39.5 s       7.3 s     20~26 t/s     11~15 t/s
Qwen3-0.6B        27.9 s       5.2 s     45~66 t/s     12~18 t/s
差距              1.4 倍       1.4 倍    约 2.4 倍      差不多
```

0.6B 的优势几乎全在 prefill；到了 1000+ 深度，两者的 decode 都掉到 12 t/s 上下，
和旧速率表里「0.6B 在深上下文下优势被吃掉」的结论一致。

## 5 结论（已核对）

```text
单轮（1700 in / 100 out）
  冷启动           prefill 65 s + decode 约 8 s ≈ 73 s
  命中前缀         3.4~10.4 s（首轮之外全部落在这一档）
一条轨迹（5~8 轮）
  system 已预热 + 开前缀缓存    25~60 s，平均 39.5 s
  完全冷启动（system 也未缓存） 再加约 38 s，即 65~100 s
  关前缀缓存                   308 s（sc_T1_001，重复 prefill 6988 token）
  缓存带来的加速               4.5 倍
瓶颈            100% 在 prefill；decode 11~15 t/s，几十个 token 只要 1~3 s
速率            prefill 单轮新增约 200 token 时 20~26 t/s（带预热），高于旧速率表的 18.4（无预热）
温度            电池 32.7 → 35.3 °C，整场未见降频
```

## 6 system 段预热的效果（已实测）

连续跑不同样本时，每个样本的首轮都在复用同一段 system KV：`命中` 1069~1087 token，
新增只有 1~35 token，TTFT 落到 0.16~1.93 s；而完全冷启动时同一件事要 38.5 s。
也就是说 boss 说的「把最长的系统提示词提前存进去」在 llama-server 上不需要额外机制——
服务起来后先发一次带 system 的请求，后续所有请求就都吃到这份 KV。
能不能跨服务重启保留（`--slot-save-path`）还没试。

## 7 已排除的疑点

早先记录的两个异常都已定位为**回放脚本自己的 bug**，与手机无关：

```text
现象   单轮模式报 predicted_n=1、0.00 ms，却返回一段完整 JSON；prompt 也比顺序跑多 42 token
根因   prefix = messages[: 2 + 2 * (len(messages) - 2) // 2]
       Python 里 * 与 // 同级左结合，先算 (2*9)//2 = 9 再加 2 = 11，
       等于把整条消息列表（含教师最后那条 finish 助手消息）都发了出去
后果   模型看到对话已结束只吐 1 个 token；服务端把末尾助手消息当续写前缀回显；
       那多出来的 42 token 正是这条助手消息
修复   先算 pairs，再写 messages[: 2 + 2 * pairs]；修后 prompt=1700、decode=42 token，全部自洽
```
