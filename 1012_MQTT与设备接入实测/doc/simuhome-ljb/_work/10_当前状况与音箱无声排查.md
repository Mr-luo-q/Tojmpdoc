## 2 音箱为什么没声音：逐段验证

先说结论：**从 HA 到 Windows 音频引擎这一段全通，而且证据表明声音真的被渲染进了音箱那一路端点。
所以问题不在 HA / MQTT / 桥 / Windows 选设备这几层，而在端点之后或电平本身。**

命令链的每一段都取到了读数：

```text
HA  switch.bt_speaker = on，number.bt_speaker_volume = 23        【已核对】
 ▼
MQTT  bt_speaker/v1/state = ON（retained），发布者 online          【已核对】
 ▼
桥    「收到命令：ON」→「开始播放 announce.wav（2.5s，loop=True，device=4）」 【已核对】
 ▼
设备  PortAudio #4 = [MME] 耳机 (EARZER SAB6)，且它就是系统默认输出   【已核对】
 ▼
会话  PID 59400 python.exe 音频会话 state=Active                    【已核对】
 ▼
端点  电平表：默认端点最大 0.300（放的是幅度 0.300 的稳态音），
      笔记本自己的 扬声器 (Realtek(R) Audio) = 0.000                【已核对】
```

被排除的四个假设：

```text
选错设备       Realtek 端点 0.000、SAB6 端点 0.300 ⇒ 音频只去了音箱那一路
被静音         端点 GetMute()=False；python.exe 会话音量 1.0 ⇒ 没有静音
Host API 选错  上一轮留下的假设（"MME 只收流不出声"）不成立：
              MME #4 已经把信号送进端点混音，而 DirectSound/WASAPI 送的是同一个端点，
              换档不改变送到蓝牙的内容。
循环没生效     11 秒跟踪显示每 2.5 秒一次脉冲（1.5s / 4.0s / 6.5s / 9.1s），循环正常
```

剩下两条，都需要现场确认：

```text
① 电平太低、声音太短
   announce.wav 是衰减音：文件峰值 0.426，最后 0.5 秒只有 0.007。
   23% 音量下，端点上实测峰值只有 0.02~0.03（约 -30 dBFS），
   每 2.5 秒只响约 0.5 秒。
   `_work\04_蓝牙音箱MQTT桥.md` 10.4 节记过同一件事：当时是"音量只有 15%"。
   另外端点 QueryHardwareSupport() = 6，即这个端点不支持硬件音量，
   23% 是 Windows 在软件里直接乘上去的——乘完确实很轻。

② 音箱侧
   音箱自己的音量/输入（它上电时的音量，或者被多点连接的另一台设备占了），
   或者它压根没在放这一路。
   查法：把系统音量拉到 100%（或 python _work\bt_speaker\tone_test.py --volume 100）
        播一段稳态音；听得到 ⇒ 就是①；听不到 ⇒ 去动音箱自己的音量旋钮。
```

## 5 第二轮（22:45 之后）：四路矩阵与新的排除

用户反馈"还是没声音"之后，把 `tone_test.py` 扩成能按名字选设备、并播 N 声短音
（每声 0.4 秒响 + 0.25 秒静，听的人只要数几声就知道哪一路通了），跑了四路：

```text
A  1 声  #5  [MME] 扬声器 (Realtek(R) Audio)   笔记本自己的扬声器，耗时 3.35s ✅ 播完
B  2 声  #4  [MME] 耳机 (EARZER SAB6)          桥现在用的这一路，耗时 1.39s ✅ 播完
C  3 声  #29 [WDM-KS] Output 1 (@System32\drivers\btha2dp.sys…)   ❌ Invalid device [-9996]
D  4 声  #33 [WDM-KS] Output 2 (@System32\drivers\bthhfenum.sys…) ❌ Invalid device [-9996]
```

结论：**WDM-KS 那两档这次连流都开不起来**（`check_output_settings` 通过但 `Pa_OpenStream` 报 -9996），
和 `_work\04` 第 10.2 节记的一致。也就是说"绕开 Windows 音频引擎直通驱动"这条路
在当前机器上不存在，能用的只有引擎路径（MME / DirectSound / WASAPI），
而它们送进的是同一个端点混音——**换档不可能改变送到蓝牙的内容**。

所以第二轮的判断没有变，只是更硬：**PC 侧一路到端点都是通的，断点在端点之后

```text

2  音箱上切换输入模式（有的音箱连着蓝牙却在放 AUX/TF）
```

```text

音箱（SAB6 A2DP 端点）        听不到   ⇒ 引擎已经把样本送进端点，但没从音箱出来
```

补充读数：

```text
Microsoft-Windows-Audio/Operational 里，22:16 / 22:22 / 22:25 各有几十条
  "MMDevAPI: Audio device state changed" —— 那几分钟蓝牙音频设备被反复插拔/切换
  音箱的 A2DP 源设备（Microsoft Bluetooth A2dp Source）安装状态正常、ProblemCode 0
当前用户 TOM\Tom 不是管理员 ⇒ pnputil /restart-device 这类强制重建链路的手段跑不了
```

所以新增 `_work\bt_speaker\relink_a2dp.ps1`（管理员运行）：

## 7 第四轮：手机能放，PC 侧 relink 要求重启

用户确认音箱是 ERAZER SAB6，且手机连它播放正常 —— 音箱本体（喇叭/功放/音量）彻底排除。
于是断点只剩"PC → 音箱"这条蓝牙音频流。23:06 用提权脚本
`_work\bt_speaker\relink_a2dp.ps1` 对 A2DP 源设备跑了 `pnputil /restart-device`：

```text
pnputil 返回 3010 = ERROR_SUCCESS_REBOOT_REQUIRED
（"需要重新启动系统才能完成配置操作"）—— 设备重启被挂起，单独这招没用成
端点重列后仍 Active，放 2 声短音仍待用户耳朵确认
```

下一步收敛成两件事（都不依赖管理员）：

```text
1  手机蓝牙关掉（如果还没关），排除多点抢占
2  Windows 设置 → 蓝牙和设备 → EARZER SAB6 → 删除设备 →
    音箱关机重开进配对 → 重新配对 → 再测
3  还不行就重启电脑（顺便把上面排队的 3010 重启请求完成）
```

## 8 结局：蓝牙栈卡死，重启蓝牙服务后出声

用户确认音箱就是 ERAZER SAB6，且手机连它播放正常；重新配对也试过，仍无声。
最后一轮用提权脚本把 **bthserv + bthHFSrv（蓝牙栈）+ Audiosrv（音频服务）** 整体重启，
之后音箱恢复出声（用户反馈"有了有了"）。

```text
根因    PC 侧蓝牙 A2DP 音频流卡死：链路和端点都"看着在"，但音频没有真正走通。
        Windows 渲染、端点电平表有信号、手机能放——这三件事都成立却无声，
        唯一的解释就是 A2DP 流本身卡住，重启蓝牙栈把它清掉后恢复。
见效动作 Restart-Service bthserv / bthHFSrv / Audiosrv（配合 pnputil restart-device）。
注意    pnputil 对 A2DP 源设备返回 3010（需要重启），单独这招没用成；
        真正起效的是重启蓝牙栈。
```

```text
⇒ 恢复音箱后，HA→MQTT→桥→音箱 这条链还要把上面这些重新拉起来才能用
```
