# 05 方案 B：房间信息前置，做成按家共享的固定块

> 核对时间：2026-10-13
> 依据：`02_端侧实测结果.md` 的实测速率与 token 画像、`04_方案A_预置固定头_保持协议.md` 的成本模型
> 状态：**未实施**，属于改协议；本文是实现规格，不是现状说明
> 前置条件：先跑完方案 A 拿到基线数字，再等 boss 确认"去掉 observe_home"可接受
>           （涉及任务难度与论文卖点），然后才动 A_policy 与工具表

## 1 目标

让 `[system + 这份家的房间/设备清单]` 成为**与任务无关**的前缀块，按"家"预热一次，
之后每一句用户话只需算它自己的十几 token。

```text
方案 A   固定头里夹着用户话        → 跨任务共享不了，每条都要付 46 s 预置成本
方案 B   用户话挪到固定块之后      → [system + 房间清单] 按家固定，一次预热长期复用
```

共享粒度是**按家**，不是全局：换一套房子要重新预热一次它的房间块。

## 2 消息结构改造

```text
现在（5 个工具）
  [0] system      A_policy + 工具表（含 observe_home）
  [1] user        用户那句话
  [2] assistant   {"name":"observe_home","arguments":{}}
  [3] user        observation: 房间清单
  [4] assistant   下一步…

方案 B（4 个工具）
  [0] system      A_policy' + 工具表（去掉 observe_home）
  [1] user        home: {"rooms":[…],"devices":[…]}
  [2] user        用户那句话
  [3] assistant   下一步…
```

两处变化：房间清单从"模型问出来的 observation"变成"系统预置的一条消息"，并挪到用户话之前；
工具表少一个工具。

两种落地写法：

```text
B1  把房间清单并进 system 段
    好处：保持"一条 system + 一条 user"的原形状，改动最小
    代价：system 随家变化，工具的语法约束也被裹进这个按家变化的块里

B2  房间清单单独作为一条 user 消息（推荐）
    好处：两级前缀，[system] 全局共享、[system+房间清单] 按家共享
    代价：出现两条连续的 user 消息，要用实机确认 Qwen 的 chat 模板渲染正常
```

## 3 连带改动清单

```text
A_policy.md      "观察怎么用"一节删掉 observe_home 那一行；
                 新增一句说明"家里的房间与设备清单已在上下文里，不必再问"
工具表           5 个减到 4 个；B_tool_schema 与数据里的工具一致性校验要同步改
D5 管线          注入 home 块；不再跑 observe_home 那一跳；
                 turns 记录少一轮，final_state 与 labels 的生成逻辑要复核
数据集           现有 1000 条轨迹的消息结构随之改变
                 → token 画像与已有实测口径作废，要么重算画像，要么重跑一批
标签             C-1 协议（finish / truncated / TOO_MANY_TOOL_CALLS）不受影响；
                 C-3 观察要求（required_observations）要复核，实际只有 T4 非空
```

## 4 收益模型

```text
预置成本（按家一次）   system 1069 + 房间清单约 120 ≈ 1200 token ≈ 46 s
                      同一个家后续所有任务都复用，不再重算
每条任务的 prefill     只剩用户那一句 19~35 token ≈ 1 s
单轮 TTFT             1~2 s（对比现在命中 system 后的 3~10 s）
一条 4 轮轨迹          ≈ 1 s + 3×(每轮增量约 150 token ÷ 26 t/s) + decode
                      ≈ 20 s 上下（对比方案 A 的 30 s）
```

收益成立的前提是"同一个家被反复提问"。若每个任务都用不同的家，这条收益不成立——
那就退化成"按家预热一次、只用一次"，与方案 A 没差别。

## 5 风险与代价

```text
KV 作废        工具表一变，system 段就变，之前预热的 KV 全部失效，必须重新预热
按家共享       换房子要重预热；多套房子并行时要为每套留一份 KV，
               4 个槽够不够要实测
研究层面的影响  observe_home 是"发现链"的第一跳。去掉它等于把任务难度降一级：
               模型不必再自己发现房间，环境直接告诉它。
               若论文卖点是发现链 / 空间推理，这个改动会削弱卖点；若只是端侧部署优化则无妨。
               这一条要先和 boss 对齐
数据可比性     消息结构变了，现有 1000 条轨迹的实测数字（39.5 s/条、累计 6988 token）
               不能直接和新结构对比，要重算口径或重跑一批
```

## 6 验收标准

```text
1  预热后连续打 5 条同一套房的用户话，首轮命中恒等于固定块长度，TTFT 稳定在 1~2 s
2  间隔 5 分钟后再打一条，命中不掉（确认 --cache-idle-slots 的默认行为）
3  换一套房子的任务，按家预热后同样成立
4  单轮平均墙钟与方案 A 对比，差值要能对上"省掉 observe_home 那一跳"的估算
```

## 7 实施顺序

```text
第一步  先跑方案 A（脚本已就绪），拿到"稳定态单轮"的基线数字
第二步  和 boss 确认"去掉 observe_home"是否可接受（涉及任务难度与论文卖点）
第三步  改 A_policy 与工具表，同步 D5 管线，重算或重跑一批数据的 token 画像
第四步  按第 6 节四项验收，结果回填本目录
```

## 8 原型实测（2026-10-14，手机真机）

不改主线，另建原型脚本 `protoB/protoB_replay.py` 在本机与手机之间跑通。样本 `sc_T1_001`。

```text
变体    固定块预热   4 跳计时   含预热总账   单跳平均   第 0 跳 TTFT
rooms   40.1 s      26.7 s    66.9 s      6.7 s      1087 ms
full    60.8 s      30.8 s    91.6 s      7.7 s      1331 ms
对照：基线（5 工具、含 observe_home）67.5 s；方案 A 42.9 + 24.0 = 66.9 s
```

### 8.1 协议层能不能行：能

llama-server 接受"两条连续的 user 消息"（`system' + home 块 + 用户话`），Qwen 的 chat 模板
渲染正常，模型正常产出 JSON 工具调用。这是 B2 写法最大的未知项，现在确认了。

### 8.2 模型行为变了：它会跳过必要的验证，而且会猜 device_id

```text
基线 / 方案 A（5 工具、没有 home 块）
  第 0 跳  {"name":"inspect_room","arguments":{"room_id":"room_kitchen"}}     ← 顺序正确

方案 B（4 工具、home 块已给房间）
  第 0 跳  {"name":"execute_action","arguments":{"device_id":"device_kitchen_fridge",
           "action":"set_temperature","params":{…}}}                        ← 跳过 inspect_device
  第 1 跳  {"name":"inspect_device", …}                                     ← 补看，但已经晚了一步
  第 2 跳  {"name":"execute_action", …}
  第 3 跳  {"name":"finish", …}
```

两件事值得警惕：

```text
① 违反硬规则   A_policy 明写"还没 inspect_device，不要 execute_action"，B 形态下它第一步就违了
② 猜 device_id  rooms 级 home 块里根本没有 device_id，模型凭空写出 device_kitchen_fridge
                 —— 命名规律 device_<房间>_<类型> 太透明，它用语言先验猜对了
   full 级（把 device_id 明给）行为完全一样 → 说明它本来就在猜，给不给前置信息都一样
```

也就是说：**预置房间信息会削弱发现链，而且削弱得比预期更狠**——模型不只是省掉 observe_home，
它把 inspect_device 也一起跳过了。这条要在第 5 节"研究层面的影响"里再加重一笔。

### 8.3 full 级不值得

`full` 比 `rooms` 贵 24.7 s（预热多 20.7 s、计时多 4 s），换来的只是"提前给出 device_id"，
而模型自己会猜，行为没有任何改善。要做就做 `rooms` 级。

### 8.4 按家共享在现有数据集上不成立

查了全部 1000 条样本：与 `sc_T1_001` 户型（房间 + 设备布局）完全一致的**只有它自己**——
每个样本的家都是随机生成的，家不重复。所以"按家共享"只在**真实部署**（一个固定的家反复提问）
才成立；在数据集回放口径下，B 相对 A 拿不到额外收益。

### 8.5 一个工程坑

连续跑多次后 llama-server 会自己退出（日志末尾 `cleaning up before exit`），中间那次请求返回 400，
重启后立刻恢复正常。4 个 slot 的 KV 池会被多次不同的长前缀塞满，建议每跑一批就重启服务，
或把 `-c` 调大、关掉 `kv_unified`。
