# midea_listen.py

## 职责

连上美的温湿度计，订阅它所有可通知（notify/indicate）的特征，记录设备主动推来的数据；
同时定时重读那些"read,write"型厂商特征，看数值会不会变。

## 为什么需要它

`midea_probe.py` 的结论是：这台设备能连、能读、不需要配对，
但它对外只有三个厂商服务，每个是一对"read,write + read,indicate"，
直接读全是 0。数据只可能通过两条路出来：订阅通知、或者写命令去问。
这个脚本先把第一条路走完。

## 输入

```text
--address   设备地址，默认 50:5E:3A:E9:93:2C
--window    等设备出现的总窗口秒数，默认 300（设备只在被唤醒后广播几分钟）
--duration  连上后听多久，默认 90 秒
--interval  重读与重连的间隔，默认 15 秒
依赖        bleak（树莓派上已装 0.11.0）
```

## 输出

```text
连接过程（每次尝试一行）
每个可通知特征的订阅结果（成功/失败）
收到的每条通知：[时间戳] 特征短 UUID  十六进制载荷  (长度)
每轮重读时"数值发生变化"的特征（没变就不打印）
结尾：各特征收到多少条通知
```

## 读取

设备的可通知特征（订阅）与可读特征（轮询读）。不写任何特征。

## 写入

无。写命令那条路（如果订阅拿不到数据，就得逆向 App 写的命令）留到下一步再评估。

## 不负责

不解析温湿度数值（要先确定载荷格式）、不配对、不写 MQTT、不逆向私有协议。

## 失败时返回什么

```text
连不上        重试到窗口用完，退出码 1
订阅失败      打印异常继续订阅下一个
一条通知也没收到   正常退出，统计里写"一条通知都没收到"（这本身就是结论）
```

## 判定口径

```text
订阅后收到会变的载荷        → 能接：按该载荷写解析即可
只有初始化/心跳类固定载荷   → 得看写命令那条路
完全没有通知               → 数据只能靠写命令问，成本高一个量级
```
