# 手机跑 0.6B / 1.5B：提速空间与复现实验

调研与来源核验日期：2026-10-14。主要对象为仓库当前的 Redmi K70E / 天玑 8300-Ultra，兼顾前一台华为 Pura 70 Pro+ / Kirin 9010。模型分别指 **Qwen3-0.6B Q4_K_M** 与 **Qwen2.5-1.5B-Instruct Q4_K_M**，不能把参数规模相近的其他模型直接代入结论。

**有提速空间。已经有手机实测支持的是线程配置、选用较小模型；在现有 `-t 4` 基础上，最值得继续验证的是 CPU 优化内核、长上下文的 Flash Attention / KV 量化，以及前缀缓存带来的首字延迟下降。当前证据不能承诺再翻倍。** Mali Vulkan 的已有结果不支持直接改用 GPU，但也不足以排除所有 Mali 推理框架。

本轮 ADB 枚举没有连接设备，因此新增的是资料取证、源码核对、复现程序与电脑侧验证，没有新增手机 t/s。历史手机速度按来源保留；源码证实的行为、推断与待测结果分别注明。

> 后续进展（2026-10-14 当天）：设备接入后已完成真机实测，结果见 [手机提速实测结果-20261014.md](手机提速实测结果-20261014.md)。本文中的“待测”项在该文档里按实测结果更新。

## 设备与历史数据：哪些可以作为起点

设备判断优先采用原始日志，其次设备官方规格，最后历史报告中的解释。仓库的 `probe-reports/probe-7LPRYTBYU8NRY5SC-20261009-152022.log` 开头依次记录系统 release 为 **16**、SDK 为 **36**，内核名含 `android14-11`。内核构建分支名不能代替 Android 系统版本，旧文档中的“Android 14（SDK 36）”需要据此纠正。

| 项目 | 可核对的事实 | 实验含义 |
|---|---|---|
| K70E / MT6897 | 官方规格 4×Cortex-A715 + 4×Cortex-A510 [S15] | cpu7 的高频分组不能证明它是 A720 |
| CPU 频率分组 | 原始日志 cpu0–3 上限 2.2 GHz，cpu4–6 3.2 GHz，cpu7 3.35 GHz | 可按编号测试亲和性，CPU 微架构由规格/MIDR确认 |
| CPU 特性 | 原始日志包含 `asimddp`、`i8mm`、`sve`、`sve2`、`svei8mm` | 有优化内核可用的硬件条件，尚未证明已安装二进制实际使用它们 |
| 内存 | 历史运行 `MemAvailable` 约 6.9 GiB，设备报告约 12 GB RAM | 两个模型单实例能容纳；可用内存不等于已达到内存带宽上限 |
| Mali-G615 MC6 | 正确 Android Vulkan loader 后可枚举真实 GPU | 初期“GPU 不可达”结论已被后续测试修正 |
| APU/NPU 780 | NNAPI 枚举到 MTK 设备；ADD 例程建图失败 | 枚举成功、执行成功、LLM 加速成功是三个独立验收点 |
| 运行时 | Termux 包报告 llama.cpp 0.6.0、build 0 / commit unknown | 包版本并非充分的二进制身份；复现时保留包版本、哈希和构建文件 |

下表记录同批历史对照，不拼接不同批次的最高值。

| 对照与出处 | 1.5B | 0.6B | 可支持的判断 |
|---|---:|---:|---|
| K70E 线程扫描，tg64，t8→t4；`CPU性能实测报告.md` §2.2 | 7.80→16.32 t/s，**2.09×** | 18.01→33.75 t/s，**1.87×** | 修正线程数收益明确；已经采用 t4 时不能再计算一次这项收益 |
| K70E 定稿默认 t4 / 绑 cpu4–7 t4；同报告 §2.4 | 14.57 / 14.56 t/s | 33.64 / 33.64 t/s | 该批显式绑核没有收益；可测长期稳定性，不能预告涨速 |
| K70E 四模型同批，pp128 / tg64；`四模型架构与性能对比.md` §3.1 | 28.54 / 18.86 t/s | 80.41 / 43.19 t/s | 同批换 0.6B，pp 2.82×、tg 2.29×；不是 1.5B 原模型的等质量加速 |

仓库现存完整程度最高的 CPU 速度原文是 `probe-reports/perf-lean-1.5B-prefill.log`：可以核对 pp32～pp2048 的 18.28～17.70 t/s；该次在 pp4096 被终止，没有得到完整的后续曲线。其他报告中很多数据的原文只标注为手机 `~/*.log`，本轮无法重新取回。它们是**历史报告转述**，与仓库保留的原始日志分开使用。

## 先修正测量解释，避免优化错方向

| 旧判断 | 本轮核对结果 | 对复现的影响 |
|---|---|---|
| `-p 128 -n 64` 就是处理128后生成64 | v0.6.0 和固定新版的测试构造分别设置 pp 的 `n_gen=0`、tg 的 `n_prompt=0` [S01/S02/S21] | 指定已有上下文用 `-d 128 -p 0 -n 64`；连续负载用 `-pg 128,64 -p 0 -n 0` |
| 非流式 curl `time_starttransfer` 是首字延迟 | 首包可能是响应头或完整响应，非流式没有提供首个答案 token 的到达时间 | 用 SSE 测首个非空 `content`，同时区分空 role 事件和 reasoning |
| backend 列显示 Vulkan 就证明张量在 GPU | 两版 `get_backend()` 遍历已注册后端名称，未检查逐算子或逐张量放置 [S02/S21] | 该列单独不能证明 `-ngl 0` 被 GPU 接管；核对加载/张量日志并用显式 CPU 或 CPU-only 构建 |
| 电池 28～37°C 足以排除热降频 | 电池温度与 SoC 热点、厂商限制阈值不是同一读数；Android 提供热状态/余量 API [S17] | 不能从电池温度排除 SoC 热限制；需要电源条件对照、持续采样及可用热状态 |
| 20 次 sysfs 1800 MHz 证明永久锁频 | 仅证明该采样窗口的节点读数；后续报告记录 cpu4 1300～2800 MHz | 频率读数也可能反映请求/策略状态，尚未确定唯一根因；不能许诺升到3.2 GHz就快1.78倍 |
| t4→t8 变慢证明内存带宽到顶 | 还可能涉及异构核等待、线程同步、调度和缓存开销 | 定位候选瓶颈需要内核/线程/亲和性对照；仅模型大小×t/s不能测出DRAM真实带宽 |
| 温升与 t/s 的比值是“每瓦性能” | 温升不等于瓦数，也不是能量 [历史提速报告] | 称为温升观察；测 J/token 需能量积分和空闲功耗校正 |

预热同样要控制。`--no-warmup -r 2` 只跳过显式预热，并不会清空页缓存、重启服务或让第二次运行回到冷态。旧报告中的“每次全新请求”“预热让CPU升频”的因果解释未被这一个开关充分证实。新协议默认保留预热，并单独测服务冷启动。

关闭 Qwen3 思考已有源码证据：v0.6.0 的 `--reasoning off` 会写入模板参数 `enable_thinking=false` [S22]；官方 Qwen3 同样说明模板控制 [S14]。`--reasoning-format none` 只是输出解析方式，不代表关闭思考。未来版本按自己的 `--help` 核对，不能把相似参数名视为等价。关闭思考缩短答案等待和总生成量，不应宣传为底层 token/s 翻倍。

## 为什么 0.6B 尤其值得测 FA 与 KV 量化

已归档官方模型配置 [S18/S19] 与仓库 GGUF 元数据一致。按 f16、完整注意力计算：

```text
每 token 的 K+V 字节 = 层数 × KV头数 × 头维度 × 2(K和V) × 2(f16字节)

Qwen2.5-1.5B  28 × 2 × 128 × 2 × 2 = 28 KiB/token
Qwen3-0.6B    28 × 8 × 128 × 2 × 2 = 112 KiB/token

Qwen3 查询头=16、KV头=8，GQA=2:1；旧文档“8:8、1:1”标注不对。
```

| 实际缓存 token 数 | 1.5B f16 KV | 0.6B f16 KV | q8_0 / q4_0 理想数据体积 |
|---|---:|---:|---|
| 512 | 14 MiB | 56 MiB | 约 f16 的 53.1% / 28.1% |
| 2048 | 56 MiB | 224 MiB | 1.5B 约29.75 /15.75 MiB；0.6B 约119 /63 MiB |
| 4096 | 112 MiB | 448 MiB | 继续近似线性增长 |

表中 q8_0 按32个值34字节、q4_0按32个值18字节估算，含量化块缩放但未计对齐、额外工作区和布局。分配容量还受运行时配置影响，以实际加载日志为准。**量化 KV 减少存储与读取，反量化又增加计算，体积比例不等于速度比例。**

Flash Attention 的作用是改变注意力的分块与中间数据读写，减少大中间张量；它和 KV 量化是两项不同变量，应先 off/on 比较，再在 FA on 下比较 f16/q8_0/q4_0。量化 V 的可用性依赖运行时和 FA 支持，启动时报不支持就记录失败，不改成别的配置仍称成功。[S01/S03]

`-c` 是允许的上下文容量，`-d` 是基准已经填充的上下文深度。`-c 4096` 实际只用500 token，不能直接套用 d4096 的吞吐。减小容量能降低分配压力；减少真正送入的历史 token 才会直接改变每步注意力负载。

## 提速路线及投入顺序

| 顺序 | 路线 | 最可能改善 | 当前证据 / 代价 | 本机尚待测 |
|---|---|---|---|---|
| 先校准 | 显式 CPU、单实例、t2/3/4/6/8，单独选 `-tb` | 吞吐与稳定性 | t8→t4 已证实；更细扫描成本低 | t2/3 与持续负载；prefill最优线程数可能不同 |
| 第一轮 | 保留服务、固定前缀、缓存命中、关闭多余思考 | 首字与答案完成时间 | 官方接口支持缓存；无需转换模型 | 用真实 SSE 量测命中与未命中 |
| 第一轮 | FA off/on，再量化 KV | 深上下文的 decode / 内存 | 0.6B KV约四倍，针对已有衰减有明确机制 | 浅/深上下文分别测；中文质量回归 |
| 第二轮 | 同版通用 CPU vs i8mm 优化 / KleidiAI | prefill和可能的decode | 官方源码支持 ARM 特性、重排和 KleidiAI [S04/S23/S27/S29] | 已安装包缺少内核使用证据；增幅未知 |
| 第二轮 | Q4_K_M vs Q4_0；必要时Q3_K_M或Q8_0 | 权重读取、内核适配 | 量化格式改变实际字节和可用内核 | Q4_0不保证更快；0.6B低比特质量更敏感 |
| 第二轮 | 标准/性能模式、插电/电池、散热配对 | 持续速度和pp | 系统限制为候选解释，华为有热机衰减记录 | K70E的SoC热状态和真正限制来源 |
| 第三轮 | MNN CPU / OpenCL，MLC Android GPU | 另一套内核/算子图 | 需要转换、固定框架和量化；详见后文 | 本机尚无受控对照 |
| 条件性 | n-gram / draft 推测解码 | 重复文本或高接受率任务 | 上游提供对应机制 [S03/S08] | 1.5B目标配0.6B草稿未必能偿还草稿开销 |
| 门槛最高 | MediaTek NPU运行时 | 多数期望在prefill | GGUF不能直接变成NPU图；NNAPI已弃用 [S16] | 780匹配delegate、模型包和真正NPU执行证据 |

有时更小的存储格式反而慢：例如某量化格式解包开销更高，或者没有对应向量内核；也有可能 Q4_0 因特定打包内核超过 Q4_K_M。必须把“权重档位”和“运行时构建”组成实验矩阵。新版 KleidiAI 实现明确出现 Q4_0、Q4_K、Q8_0、Q6_K 路径 [S27]，不能沿用“它只加速Q4_0”的旧经验。混合 Q4_K_M 的张量能否全部使用这些路径仍需日志和实测。

0.6B和1.5B本身已是小模型，非结构化剪枝在普通稠密 GGUF 中仅把数值置零，不会让相应内存位置消失，也不会让稠密kernel自动跳过。结构化剪枝会改变维度，但需要重新导出、校准和质量恢复，投入高于先做内核/缓存实验。蒸馏属于训练项目。proot/Docker不会自动提升核心矩阵计算速度，不安排在首轮。

推测解码要先核算草稿成本：本机同批0.6B约43.19 t/s，相当于每步23.2 ms；1.5B约18.86 t/s，每步53.0 ms。草稿虽小，但也消耗CPU与内存。只有 `k×草稿单步时间 + 目标验证时间 < 接受的输出token数×原目标单步时间` 才有净收益；其中验证时间和接受率必须实测，不能用大批pp128替代短候选批的验证时间。小模型作目标时更适合先试不加载第二模型的n-gram候选，通常只对重复/模板文本有优势。[S03/S08]

阶段拆分“GPU/NPU做prefill、CPU做decode”还需要同一运行时支持状态交接，并记录KV布局转换、同步与权重驻留成本。改 `-ngl` 只控制层卸载，不等于自动实现按阶段分工。现有Mali Vulkan连prefill也较慢，没有证据支持本机优先实现这种调度工程。

## GPU、MNN、MLC、ExecuTorch、NPU怎么取舍

仓库的 Mali Vulkan 最好记录之一是 0.6B 全量卸载 tg22.80，低于该次 CPU33.64；1.5B全量卸载还出现超时。之后 `Token速率详表.md` 有同批CPU/GPU对照，仍支持“当时 llama.cpp Vulkan 栈收益差”。`int dot:0`、`matrix cores:none` 只是该驱动向该后端暴露的能力，不能单独推出“Mali硬件不适合所有LLM”“重编译绝无收益”。原始 GPU 压测日志未完整归档，也不能把跨环境数值当作最后的严格归因。

| 路线 | 需要交付的可运行资产 | 本机评估方式 | 停止投入条件 |
|---|---|---|---|
| llama.cpp CPU | 原有GGUF + 隔离CPU-only二进制 | 同权重、同提交，generic/i8mm/KleidiAI比较 | 内核有证据但吞吐/TTFT均无改善 |
| llama.cpp OpenCL | 实际Mali OpenCL设备及通用kernel构建 | 先确认不是软件设备；上游主要验证Adreno [S07] | 只有设备枚举、算子不支持或稳定比CPU慢 |
| MNN CPU/OpenCL | 原始HF模型导出的MNN权重、tokenizer、config、Android运行库 | CPU4线程和OpenCL分别跑llm_bench与同题中文输出 [S09/S24/S25] | 转换/图不兼容，或受控结果无收益 |
| MLC Android | 转换后的权重、针对Android编译的model library、APK | 按Android文档构建，确认实际OpenCL设备 [S10] | 对照tokenizer/量化质量不成立或无法使用Mali |
| ExecuTorch XNNPACK | PyTorch导出并lower的.pte，配套tokenizer和移动runtime | 先确认对应Qwen导出链；XNNPACK是CPU路线 [S11/S28] | 只有通用后端支持声明，没有本模型完整导出 |
| LiteRT-LM | .litertlm模型包、Android SDK、匹配NPU native libraries | API支持CPU/GPU/NPU，但库/型号匹配还需核实 [S12/S26] | 找不到APU780可分发的delegate和兼容模型包 |

旧报告所引论文 [S20] 本轮取到了完整原文。它在**小米14、Qwen2.5-1.5B w4**上，MNN CPU decode为 **45.7**、llama.cpp CPU为 **34.5**；小米17对应结果又是 **19.0** 和 **51.6**。这两个具体例子足以说明性能由设备、版本、量化和路径共同决定。只引用小米17那一格排除MNN，或宣称“NPU永远慢于CPU”，都超出了证据。论文中的高通 GENIE、其他手机的峰值不能作为天玑8300的收益承诺。

NPU还有接入门槛：NNAPI从Android15起被官方标为弃用 [S16]，弃用不等于本机接口立刻消失；仓库ADD例程的 `BAD_DATA` 说明尚未通过建图参数校验，不能证明硬件执行失败。Python中没有 `NnApiDelegate` 属性也不能单独证明底层二进制完全没有delegate，但现有工程没有给出可用入口。应在准确SDK头文件、支持算子查询和实际非CPU执行证据之后再谈LLM速度。

LiteRT-LM的Android文档要求提供NPU原生库目录 [S26]，其项目README还提到动态KV增长 [S12]。因此“所有NPU只能固定静态大窗口”的说法也不应继续泛化。本轮仍没有证实这些库支持K70E的780。若设备支持页抓取失败，按来源索引明确标注，不能从“框架支持MediaTek”猜到“支持这代APU”。

## 实验规格与验收

```text
设备/运行时取证
  → 固定 GGUF SHA-256、二进制/库、构建提交、系统和电源条件
  → 只开一个推理实例，恢复到可比起始状态
  → A基线 → B候选 → B候选 → A基线，按模型和深度分别记录
  → 保存pp/tg原文、SSE答案、温度/热状态与频率读取结果
  → 计算吞吐与延迟，检查同题输出
  → 通过后才把候选放入日常启动配置
```

| 模块 | 职责与输入 | 输出 / 读写 | 失败行为 / 对应文件 |
|---|---|---|---|
| 资料取证 | 固定提交源码与官方文档URL | sources原文、manifest.tsv、SHA-256 | FAILED及网络原因；`tools/fetch-speed-sources.py` |
| 参数实验 | GGUF路径、bench路径、单一实验suite | metadata/help、逐调用log、频率tsv、结果tsv | 不填伪速度；A失败停止；`tools/phone-speed-bench.py` |
| SSE测量 | UTF-8提示词、模型标识、实验服务 | 完整SSE/答案、首content/reasoning/事件时间、usage | 模型不符或无可见完整响应标FAILED；`tools/measure-phone-stream.py` |
| 人工质量验收 | 同题答案与任务约束 | 每题正确性、格式、关键事实保持表 | 质量下降则拒收该配置；操作手册内的固定题集 |

核心比较条件是：相同设备、权重、tokenizer、已有深度、生成长度、并发、温控起点；内核实验相同提交，量化实验相同原始权重。跨框架的量化格式不同，要同时报告字节数和质量，而不能只把“4bit”视为同一精度。

吞吐收益计算 `median(B)/median(A)-1`；延迟改善计算 `1-median(B)/median(A)`，pp与tg分别算。短请求至少5次，并报告中位数、最小/最大与全部原文；仅5个请求不足以估计稳定p95。基准参数实验先一个ABBA块筛选，通过后再3个块和至少10分钟真实服务连续负载；长上下文矩阵可能耗时数十分钟到数小时，先单模型、单深度验证可运行性。

建议验收门槛是**至少10%中位数收益且重复块方向一致**；这是本项目的工程阈值，非论文保证或统计显著性判定。若收益与波动相当，应复测或记“没有确认收益”。持续负载看后半段稳定速率，避免用瞬时峰值作结论。质量题集必须保住全部确定性要求，并单独记录开放题评分。失败/超时不能从汇总中无痕删除。

电源实验要注明是否由USB供电。电脑走USB ADB转发测HTTP会改变“电池供电”条件；拔线实验在Termux本机运行脚本，或事先配置无线ADB。温度读不到时标“不可见”，使用者记下系统性能模式与热提示；15秒组间等待只减少连续压力，并不证明冷却到了相同状态。

若测能耗，使用电池能量计或外部功率仪，明确净能量积分 `(运行功率-同条件空闲功率)×时间` 并除以实际输出token数。插电时电池电流无法直接代表SoC总功耗。当前复现脚本只记录性能和可读频率，没有声称完成J/token测量。
